## HIGH (3)

### copy_count counts distinct volumes across ALL 'current' snapshots, so two versions on two tapes reads as two copies of one version

- **Lens / category:** schema-structure / schema-constraint
- **Evidence:** src/policy/coverage.rs:161, src/policy/coverage.rs:214-224, src/volume/session.rs:971-975, src/volume/rebuild.rs:785-792, src/cli/operations.rs:936-943, src/cli/audit.rs:1008-1010, CONTEXT.md:95-106, src/db/migrations/001_initial.sql (snapshots: no uniqueness on status='current')
- **Claim:** `snapshots.status` permits any number of rows per unit to be `'current'` at once — `session.rs:972` promotes each sealed snapshot to `'current'` and never demotes its predecessor, `'superseded'` has zero production writers (CONTEXT.md:106 calls it vestigial), and there is no partial unique index or trigger constraining it. `coverage::copy_count_expr(CoverageQuery::current_unit(..))` then counts `COUNT(*)` over `UNION`ed `'v' || cw.volume_id` across every `'current'` snapshot of the unit. The result is the number of distinct volumes holding ANY version of the unit, not the number of copies of any one version. The comment at src/cli/operations.rs:935 states the intent exactly backwards for this case: "Copies are distinct volumes everywhere now."
- **Failure:** Unit `photos`: v1 sealed on tape L6-0001, v2 sealed on tape L6-0002. Each version exists on exactly one tape. I ran the generated expression against a copy of the deployed schema and it returns `copy_count=2`. With `min_copies_for_tape_only = 2` (the value in docs/operator-guide.md:150), `unit mark-tape-only photos` (src/cli/operations.rs:936-943) passes its ADR-0008 Tier-2 gate and the operator deletes the source directory. Tape L6-0002 then fails: v2 is gone forever, and there was never a second copy of it. `audit`'s min_copies check (src/cli/audit.rs:1008), `report copies`, `report fire-risk` and `report tape-only` (src/cli/report.rs:385,540,688) all report the same inflated number, so nothing anywhere ever says otherwise.
- **Fix:** A unit's copy count must be the MINIMUM over its `'current'` snapshots of the per-snapshot count, not the union: iterate `CoverageScope::Snapshot` per current snapshot inside `copy_count_expr` (and `location_count_expr`) when `current_only` is set, and return the min. Add a companion display of which version is thinnest. Do not fix this by making `'current'` unique per unit — CONTEXT.md:95-103 is explicit that every current snapshot is live coverage, and demoting old ones would over-promise reclaimable space.
- **Verifier correction:** Substance stands; three refinements to the wording. (1) `location_count_expr` (src/policy/coverage.rs:237-247) is inflated by the identical mechanism and should be named as co-equal, not just in the proposed fix: I verified `location_count=2` when v1 is at `home` and v2 is only at `bank`, so `min_locations_for_tape_only` is defeated by the same shape in the same command. (2) Line numbers in `src/cli/report.rs` are 393, 553 and 696 (the `copy_count_expr`/`location_count_expr` calls), not 385/540/688 — the reviewer cited the scope-construction lines a few above; same three call sites, so no misattribution. (3) Drop "states the intent exactly backwards": the comment at src/cli/operations.rs:935 is correct about what it addresses (deduping two writes of one unit onto one cartridge, counting volumes rather than writes) and is merely silent on the cross-version case. Additional supporting evidence worth carrying into the issue: the reason this survived review is that the sole multi-version test fixture (src/cli/operations.rs:2736) marks the older snapshot `'superseded'`, a status no production writer sets, so the multi-'current' shape the write path actually produces has never been under test.

### bind_late commits a volume→'erased' displacement before the File 0 contact check, so a refused `volume write` erases a live volume in the catalog

- **Lens / category:** failure-modes / ordering-invariant
- **Evidence:** src/volume/write.rs:745-753, src/volume/write.rs:473-483, src/volume/binding.rs:312-356, src/volume/write.rs:804, src/volume/write.rs:818-836, src/volume/write.rs:838, src/volume/write.rs:849-855, src/volume/write.rs:122-125, src/volume/write.rs:526-547
- **Claim:** `volume_init` documents and honours the invariant "Every catalog MUTATION runs after `check_fresh_write_contact` passes and inside one transaction, so a refused init never displaces a volume" (write.rs:122-125). `volume_write` violates it: `bind_late` at write.rs:745 opens its own transaction and commits it at write.rs:483, and `bind_cartridge` inside that transaction marks every other volume open-mounted on the matched cartridge `status='erased'` (binding.rs:316-319), closes its mount (binding.rs:352-356) and logs a 'displaced' event. Four failure points then follow with the displacement already committed and nothing left to roll back: `build::build` (804), pre-write `validate` (818-836), `TapeStore::open` (838 — drive busy/not-ready is routine), and `check_fresh_write_contact` (849). The wrong-tape refusal that issue #27's contact check exists for fires *after* the damage.
- **Failure:** Volume V2 is left unbound at init because MAM was unreadable then (media_detect.rs:8 calls a failed MAM read "a common, expected case"). The operator later loads the wrong tape — the one physically holding sealed volume V1 — and runs `tapectl volume write V2`. `check_loaded_cartridge` (write.rs:526) returns Ok silently because V2 has no open mount. `bind_late` then reads the serial, matches V1's cartridge row, marks V1 `erased`, closes V1's mount, rebinds the cartridge to V2, and commits. Only afterwards does `check_fresh_write_contact` read File 0, see V1's sealed identity, and refuse the write. The command exits with an error, V1's bytes are untouched on tape, and the catalog now says V1 is erased — excluded from copy counts (cli/audit.rs:1237), from restore serviceability (cli/catalog.rs:849) and from `report copies` (cli/report.rs:1813). Nothing anywhere moves a volume out of 'erased' (the only `UPDATE volumes SET status` writers are 'erased', 'sealed', 'retired', 'quarantined'; cli/volume.rs:1166's 'active' is test scaffolding), so the operator's only recovery is hand-editing SQLite. A unit whose last copy was on V1 now silently reads as zero-copy.
- **Fix:** Move the `bind_late` call below `check_fresh_write_contact` + `reposition_for_resume(0)` (i.e. after write.rs:859), exactly as `volume_init` orders it. `bind_late` needs only `conn`, `det` and the volume row, none of which the intervening code changes, so the move is mechanical. Add a test in the `late_binding` module (write.rs ~3915-4040 currently has none that displaces anything at all) asserting that a `bind_late` displacement is not observable when the contact check subsequently refuses.
- **Verifier correction:** The defect and the fix are right; three details in the writeup need correcting. (1) It is not silent — `bind_late` calls `report_binding` when a cartridge was bound (write.rs:485-491), which prints "warning: cartridge X previously held volume \"V1\"; it is now marked erased" (write.rs:376-379). The real failure mode is that this warning is immediately followed by a hard error and a non-zero exit, which reads as "the command aborted, nothing happened" when in fact the displacement was already committed. (2) The three consequence citations (cli/audit.rs:1237, cli/catalog.rs:849, cli/report.rs:1813) are test functions, not production code; the production evidence is src/policy/coverage.rs:482-499, the single place the live-volume status list is written. The tests assert that behavior, so the substance is unchanged. (3) The trigger is a conjunction, narrower than "the operator loads the wrong tape": the target volume must have no open `cartridge_volumes` mount (init found no readable medium serial, or the row predates this branch — write.rs:116-117 notes nothing in production wrote that join before ADR-0010), AND the loaded medium's serial must match a cartridge row that already has an open mount for another volume. A mixed-era catalog (legacy unbound volumes alongside newly bound ones) is the realistic shape. Also cosmetic: the displaced event text says the volume "was displaced by `volume init`" (binding.rs:340-342) even when the displacement came from `volume write`.

### `volume init --cartridge` with no readable medium serial displaces a live volume on a typed barcode alone — ADR-0010's File 0 justification does not cover this path

- **Lens / category:** failure-modes / adr-conformance
- **Evidence:** src/volume/binding.rs:124-153, src/volume/binding.rs:227-294, src/volume/binding.rs:300-356, src/volume/write.rs:185-191, src/volume/write.rs:526-547, src/volume/write.rs:438-447, docs/adr/0010-media-generation-is-a-cartridge-property.md:45-65, src/cli/operations.rs:807-840
- **Claim:** ADR-0010:47-54 justifies the missing consent gate by saying the decision was "made against the medium's own evidence rather than the catalog's weaker claim about it" — File 0 was read off the very tape whose catalog row is being displaced. That identity holds only when the cartridge row is matched by MAM serial. When no serial is readable, `lookup_cartridge` (binding.rs:124-153) still resolves a row from the operator-typed `--cartridge <BARCODE>`, and `bind_cartridge` runs the full displacement (binding.rs:300-356) with `serial = None`. The medium that consented via File 0 is then a *different physical cartridge* from the row being erased, and the ADR's premise is simply false on that path. ADR-0010:62-64 only contemplates the serial-less case as "the volume is written unbound with a warning" — it never contemplates `--cartridge` binding without a serial. Both backstops the ADR names are vacuous here: `check_loaded_cartridge` returns Ok the moment either side is None (write.rs:532-534, 545-547), and if a serial later becomes readable `bind_late` skips already-bound volumes (write.rs:438-447), so the row never acquires one. Contrast `cartridge_mark_erased` (operations.rs:807-840), which performs the identical volumes→'erased' write behind an ADR-0008 Tier-2 consent prompt plus `--dry-run` that lists the volumes first.
- **Failure:** An operator whose `/dev/sg` node is unusable (so `sg_read_attr` always fails — the documented common case) hand-registers cartridges and drives everything with `--cartridge`. They load blank cartridge BC003 and type `tapectl volume init V9 --cartridge BC002` (one digit wrong; BC002 is the sealed tape on the shelf holding the only copy of a unit). File 0 on the loaded BC003 is blank, so the contact check passes. The transaction at write.rs:262-290 then marks BC002's volume `erased`, closes its mount, and rebinds BC002's row to V9. stderr prints the warning and the `*** unit "X" now has ZERO copies ***` line — after the commit, with no prompt and no `--dry-run`. There is no un-erase command. Worse, the catalog now claims BC002 is erased and in_use by V9, which is precisely the state that invites a follow-on physical `mt erase` of the shelf tape that still holds the only copy.
- **Fix:** Restrict the displacement to the case the ADR actually reasoned about. Either (a) refuse `--cartridge` binding to a row that has an open `cartridge_volumes` mount when no medium serial is readable — there is no witness, so this is incoherence, not risk; or (b) route that specific case through `cli::consent::confirm` with the same facts `cartridge_mark_erased` prints, and add `--dry-run`. Then amend ADR-0010 to say the no-second-gate rule applies only when the cartridge was matched by MAM serial.
- **Verifier correction:** The finding stands; three imprecisions to fix, and one part of it is sharper than stated. (a) State the end state correctly: it is the VOLUME that was on BC002 that moves to 'erased'; the CARTRIDGE row BC002 moves to 'in_use' with a fresh open mount to V9 — a volume that is physically on BC003. (b) The contradiction is doc-vs-code and ADR-vs-code, not merely an unreasoned gap: ADR-0010:62-64 states flatly that "where no serial is readable (mhvtl exposes none) the volume is written unbound with a warning", and `BindOutcome::cartridge_id`'s own doc comment (src/volume/binding.rs:82-84) says "`None` when no medium serial was readable — the volume is written unbound". Both are false whenever `--cartridge` names a registered row, because binding.rs:238-263 sources `cartridge_id` from the row and ignores `serial` entirely. The path is also untested: the only serial=None `lookup_cartridge` test (binding.rs:503-510) uses an UNREGISTERED barcode, so no test exercises serial=None + registered row + bind. (c) The `cartridge_mark_erased` contrast is slightly overstated — its ADR-0008 Tier-2 `consent::confirm` fires only when status != 'pending_erase' (src/cli/operations.rs:843-846). The `--dry-run` listing of the volumes that would be erased is unconditional (operations.rs:821-838), so that half of the contrast holds cleanly. Also worth adding as the durable half of the defect: even with no displacement, `--cartridge` with no readable serial binds the volume to a cartridge row that may not be the medium in the drive, and `check_loaded_cartridge` can never catch it afterward because both sides remain None.


## MEDIUM (23)

### snapshot delete fails with a raw FOREIGN KEY error on any snapshot that has a non-'completed' writes row

- **Lens / category:** schema-structure / schema-constraint
- **Evidence:** src/cli/operations.rs:1260-1267, src/cli/operations.rs:1312-1332, src/volume/session.rs:160-185, src/db/migrations/001_initial.sql (write_positions.stage_slice_id REFERENCES stage_slices(id); writes.stage_set_id REFERENCES stage_sets(id); writes.snapshot_id REFERENCES snapshots(id); writes.sacrificed_slice_id REFERENCES stage_slices(id)), src/db/mod.rs:70
- **Claim:** `snapshot_delete`'s only write-related guard counts writes with `w.status = 'completed'` (operations.rs:1261-1264). Its cascade then deletes `stage_slices` → `stage_sets` → … → `snapshots` by hand. But `ValidatedLayout::plan` (session.rs:160,181) inserts `writes` rows at `'planned'` and `write_positions` rows at `'pending'` BEFORE a single byte is written, and `writes`/`write_positions` hold FKs onto exactly the rows being deleted. With `PRAGMA foreign_keys = ON` (db/mod.rs:70) the very first `DELETE FROM stage_slices` violates `write_positions.stage_slice_id`.
- **Failure:** Operator stages unit `photos` v1, runs `volume write`, the session aborts or is interrupted (EOT, Ctrl-C, crash → `recover_orphaned_sessions` marks it `'interrupted'`). The snapshot is now unwanted. `tapectl snapshot delete photos 1 --force`: the completed-write guard sees 0, the command proceeds, and the first DELETE raises `FOREIGN KEY constraint failed`. I reproduced this exactly against a copy of the deployed schema with a `'aborted'` write plus one `write_positions` row: guard returns `completed_writes=0`, then `Runtime error: FOREIGN KEY constraint failed (19)`. The whole transaction rolls back, so the snapshot can never be deleted through the CLI, and the operator gets a bare SQLite message with no hint that the fix is to clear the write session.
- **Fix:** Inside the existing transaction, delete the dependent rows first, scoped to this snapshot: `DELETE FROM write_positions WHERE write_id IN (SELECT id FROM writes WHERE snapshot_id = ?1)` then `DELETE FROM writes WHERE snapshot_id = ?1`, before the `stage_slices` delete. The `completed` guard above already guarantees none of those writes represent bytes on tape. Do not instead refuse when any `writes` row exists — an aborted-session snapshot is precisely the one an operator needs to delete.
- **Verifier correction:** Accurate as written, with one tightening of scope: the trigger is not specifically an 'aborted' session but ANY `writes` row for the snapshot in any of the five non-'completed' statuses ('planned','in_progress','failed','aborted','interrupted') — `ValidatedLayout::plan` (session.rs:159-184) creates them at 'planned'/'pending' outside a transaction before a single byte is written, so even a `volume write` that dies immediately after plan leaves the snapshot permanently undeletable. Impact is an operator dead-end plus an opaque `FOREIGN KEY constraint failed` message; no data loss or on-tape corruption, and a manual SQL delete of write_positions/writes is a workaround for anyone who knows the schema.

### db fsck --repair cannot repair: its DELETEs violate the same FKs, and it never runs PRAGMA foreign_key_check

- **Lens / category:** schema-structure / operator-workflow
- **Evidence:** src/cli/operations.rs:1698-1752, src/db/migrations/001_initial.sql (write_positions.write_id REFERENCES writes(id)), src/db/mod.rs:623
- **Claim:** `db_fsck(repair=true)` runs `DELETE FROM writes WHERE volume_id NOT IN (SELECT id FROM volumes)` (operations.rs:1725) and `DELETE FROM stage_slices WHERE stage_set_id NOT IN (SELECT id FROM stage_sets)` (operations.rs:1731) in one transaction. Any orphaned `writes` row that has `write_positions` children, or any orphaned `stage_slice` referenced by a `write_positions` or by `writes.sacrificed_slice_id`, makes the DELETE raise a FK violation and rolls the entire repair back. Separately, fsck hand-rolls exactly two orphan scans while the schema has roughly thirty declared FK edges, and never calls `PRAGMA foreign_key_check` — the one statement that would cover all of them (the codebase already knows about it: db/mod.rs:623 uses it in a migration test).
- **Failure:** An operator restores a hand-edited or foreign database with `db import` (which is a raw SQLite page copy, operations.rs:1645-1650 — no FK validation at all), then runs `tapectl db fsck --repair` to clean it. fsck reports "N orphaned write records", then the repair aborts with `FOREIGN KEY constraint failed`, repairing nothing while claiming it would. Meanwhile orphaned `manifest_entries`, `stage_sets`, `snapshots`, `cartridge_volumes` and `volume_deposits` rows are invisible to it entirely, so fsck reports a clean database that `foreign_key_check` would condemn.
- **Fix:** Replace the two hand-rolled scans with `PRAGMA foreign_key_check` for reporting (it names table, rowid, parent and constraint index per violation), and for `--repair` delete children before parents — `write_positions` before `writes`, `write_positions`/`writes` before `stage_slices`. With FK enforcement ON at every `db::open`, orphans can only arrive via hand-edit or `db import`, so this is a repair tool that cannot repair rather than a corruption vector — but it is the only tool an operator has in that situation.
- **Verifier correction:** Accurate except for one detail of the operator-visible sequence: with `--repair`, `db_fsck` never gets to print anything. `cli/db.rs:47` calls `db_fsck(conn, repair)` and only prints the "fsck: integrity=..., issues=N, repaired=N" block after it returns Ok, so a repair that trips the FK returns Err and the operator sees only `FOREIGN KEY constraint failed` with no issue list at all (they would have seen the "N orphaned write records" line from an earlier plain `db fsck` run). So it is "fsck --repair dies with a bare SQLite FK error and repairs nothing", not "reports N orphans, then aborts". Everything else — the two-edge blind spot, the missing `PRAGMA foreign_key_check`, the all-or-nothing rollback, and `db import` doing no FK validation — is exactly as stated.

### cartridge_volumes.UNIQUE(volume_id) + INSERT OR IGNORE makes a rebind a silent no-op that the CLI reports as success

- **Lens / category:** schema-structure / schema-constraint
- **Evidence:** src/db/migrations/001_initial.sql:216-223, src/volume/binding.rs:359-362, src/volume/binding.rs:296-300, src/volume/write.rs:439-493, src/volume/write.rs:526-556, src/volume/write.rs:645-674, src/cli/operations.rs:865-880
- **Claim:** `cartridge_volumes` has `UNIQUE(volume_id)` — one row per volume for all time, not one OPEN mount per volume. `bind_cartridge` binds with `INSERT OR IGNORE INTO cartridge_volumes (cartridge_id, volume_id)` (binding.rs:360). Once a volume has any row, a later bind to a DIFFERENT cartridge is silently discarded, while everything around it proceeds: the displaced-mount close (binding.rs:353), the `cartridges.status = 'in_use'` update (binding.rs:369) and `outcome.barcode` (binding.rs:298, set before the INSERT) all succeed, so `bind_late` prints "binding it now" and `report_binding` names the new barcode (write.rs:485-491). `check_loaded_cartridge` (write.rs:536-546) queries only `unmounted_at IS NULL`, so it finds nothing and returns Ok — the wrong-cartridge check goes silent for exactly these volumes. `volume_write` (write.rs:645-674) never checks `volumes.status`, so an `'erased'` volume is not refused.
- **Failure:** Volume `L6-0001` is bound to cartridge A. `tapectl cartridge mark-erased A` (operations.rs:870-874) closes the mount and sets the volume `'erased'`. The operator loads cartridge B and runs `tapectl volume write L6-0001`. `volume_write` finds no unresolved session (the old writes are `'completed'`) and proceeds; `check_loaded_cartridge` sees no open mount and passes silently; `bind_late` sees no open mount, reads B's serial, and calls `bind_cartridge`, whose `INSERT OR IGNORE` does nothing. I reproduced the end state against a copy of the deployed schema: `cartridge_volumes` holds exactly one row, `(cartridge A, volume 1)` with `unmounted_at` set; cartridge B is `status='in_use'` with no volume at all. The operator is told the volume is bound to B; the catalog says it lives on A. This is the bytes-to-the-wrong-tape class that 012_cartridge_lifecycle.sql:48-53 explicitly names as the reason that table exists. Related: the "at most one open mount per cartridge" invariant that src/cli/operations.rs:542 reasons from is convention in `bind_cartridge` only — no constraint enforces it.
- **Fix:** Replace `UNIQUE(volume_id)` with a partial unique index on the fact that is actually invariant: `CREATE UNIQUE INDEX ... ON cartridge_volumes(volume_id) WHERE unmounted_at IS NULL`, plus `CREATE UNIQUE INDEX ... ON cartridge_volumes(cartridge_id) WHERE unmounted_at IS NULL` to make the one-open-mount-per-cartridge rule a constraint rather than a comment. Then change `INSERT OR IGNORE` to a plain `INSERT` so a genuine conflict surfaces instead of vanishing. Independently, give `volume_write` a `volumes.status` precondition — an `'erased'`, `'retired'` or `'quarantined'` volume should refuse before the drive is opened.
- **Verifier correction:** Accurate as stated, with three tightenings. (1) In the scenario the displaced-mount close at binding.rs:353 is vacuous — cartridge B has no open mount — so the harm comes only from the INSERT OR IGNORE no-op plus the cartridges.status update and the report; (2) outcome.barcode is binding.rs:297, not 298; (3) reachability: every path that closes a mount (cartridge mark-erased, and bind_cartridge's own displacement at binding.rs:353) also sets that volume to 'erased', so the trigger always requires `volume write` on a volume the catalog already marks 'erased' — anomalous operator sequence, but nothing refuses it, which is the finding's own second half. Consequence is catalog-vs-physical divergence, a false "bound to cartridge B" message, and a permanently silent wrong-cartridge check for that volume — not data loss, since the bytes land on a correctly blank tape whose File 0 still identifies the volume.

### Generation capacities are decimal; every operator-facing --capacity is parsed as binary, so a declared cartridge capacity over-states the tape by up to 10%

- **Lens / category:** schema-vs-code / schema-constraint
- **Evidence:** src/media.rs:137-155, src/staging/mod.rs:1181-1188, src/cli/cartridge.rs:162-171, src/config.rs:238-241, src/volume/write.rs:238-247, src/volume/write.rs:279-292, src/volume/write.rs:688-689, src/cli/cartridge.rs:265, src/cli/mod.rs:208-210
- **Claim:** `Generation::native_capacity_bytes` (src/media.rs:137-155) stores the marketed DECIMAL figures (LTO-6 = 2_500_000_000_000, LTO-10 = 30_000_000_000_000). Every string an operator can type for the other two layers of ADR-0010's capacity ladder — `cartridge register --capacity` (src/cli/cartridge.rs:163) and `backends.lto[].capacity_override` (src/config.rs:239) — goes through `staging::parse_size_to_bytes`, whose multipliers are BINARY (src/staging/mod.rs:1185-1186: G = 1024^3, T = 1024^4). The two halves of one precedence ladder are in different unit systems, and `resolve_capacity` picks between them with no normalisation before the result becomes `volumes.capacity_bytes` (src/volume/write.rs:242-247, 279-292) — the sole authority the write gate reads (src/volume/write.rs:688). `cartridge info` then divides the decimal figure by 1024^3 and labels it "GB" (src/cli/cartridge.rs:265), so the operator cannot see the discrepancy either.
- **Failure:** Run `tapectl cartridge register --barcode B40T --media-type LTO-10 --capacity 40T` — the exact declaration ADR-0010 line 98 names as the way to declare a 40 TB LTO-10. Verified live on a throwaway home: `cartridges.nominal_capacity` = 43_980_465_111_040, i.e. 9.95% more than the cartridge's real 40 TB. `volume init` copies that into `volumes.capacity_bytes` (CapacitySource::CartridgeRow beats the table), and `volume_write` computes `usable_bytes = 43_980_465_111_040 * 0.92 = 40_462_027_902_156` — MORE than the tape physically holds. ADR-0010 removed end-of-tape salvage and made the pre-flight gate the sole capacity defence, so the write runs for hours and then aborts at a real EOT with an unsealed tape. The same command also makes `cartridge info B40T` print "Capacity: 40960 GB", and `tapectl import` defaults to `--capacity 2500G` = 2_684_354_560_000, which is 7.4% larger than an LTO-6 actually holds.
- **Fix:** Parse capacity declarations with the same unit system the generation table uses: give `cartridge register --capacity`, `backends.lto[].capacity_override` and `import --capacity` a decimal-aware parser (40T = 40e12, or accept 40TiB explicitly) rather than reusing the binary `parse_size_to_bytes` that slice sizes need. At minimum, have `cartridge register` refuse or loudly warn when the declared capacity exceeds `generation.native_capacity_bytes()`, and change src/cli/cartridge.rs:265 to label its `/1024^3` figure GiB.
- **Verifier correction:** Real, but narrower in practice than "every operator-facing --capacity" suggests. The default paths are correct: `cartridge register` with no --capacity uses the decimal table (src/cli/cartridge.rs:165-171), and `volume init` with no cartridge row or drive override falls through to that same table. Inflation happens only where a human types a size string: (a) `cartridge register --capacity 40T` — the exact form ADR-0010:95-99 prescribes for a 40 TB LTO-10 — stores 43.98 TB, which resolve_capacity prefers over the table and volume init copies into volumes.capacity_bytes, so the pre-flight gate (write.rs:688-689 at 0.92) permits ~40.46 TB on a 40 TB tape; and (b) `import --capacity` defaults to "2500G" = 2.684 TB for an LTO-6, 7.4% over. The capacity_override layer is weaker evidence: its documented legitimate user is a virtual drive (config.rs:152-160) where mhvtl sizes are naturally MiB, so binary parsing there is plausibly intended. Consequence is not data loss — ADR-0010/v2 make a real EOT a clean abort to an unsealed tape — but a near-full write that passes the gate and dies hours in, with the figure unauditable because cartridge info labels a /1024^3 number "GB". - **Claim:** ADR-0011:28-29 says of `cartridge move` and `volume move` that "Both write the same two rows, so the cartridge's place and its volumes' places cannot disagree", and :75-76 that the location-count checks "stop being able to disagree with the shelf". The reasoning covers only the two move commands. It misses that ADR-0010 added a THIRD writer of the cartridge/volume relation — `bind_cartridge` — which changes which volume is on a cartridge and touches neither location column: `grep -n location src/volume/binding.rs` returns nothing, the auto-register INSERT (binding.rs:269-283) names no `location_id`, the mount INSERT (binding.rs:359-362) names only cartridge_id/volume_id, and `volume init`'s own volume INSERT (write.rs:283-285) inserts `status='initialized'` with no `location_id`. `move_together`'s comment states the resulting belief outright — "This function is the only production writer of EITHER column" (location.rs:282) — and `grep -rn "SET location_id"` confirms location.rs:319/:347 are the only production writers. A cartridge's location is also sticky for life: `cartridge mark-erased` (operations.rs:958-973) changes status and mounts and never clears `location_id`, so every cartridge whose place has ever been recorded produces a location-less volume on every subsequent init.
- **Failure:** Measured end to end on a throwaway home with the prebuilt binary. `location add bank`; `cartridge register --barcode L6-0001 --media-type LTO-6`; `cartridge move L6-0001 --to bank`; then the rows `volume init` + `volume write` produce (a volumes row with location_id NULL, an open cartridge_volumes mount, a completed write). Result: `cartridge info L6-0001` prints "Location: bank" and "L6-V1 (current, mounted ...)", while `catalog locate photos` prints Location "unknown", `report copies` prints "photos: 1 copies, 0 locations", `report fire-risk` prints "photos: 1 copies, 0 locations — below minimum (needs 2)", and `location info bank` prints "Volumes: 0". The catalog simultaneously knows the plastic is in the bank and that the only copy of the unit is nowhere, which is exactly the disagreement the ADR says is impossible. `location_count_expr` (coverage.rs:237-247) counts only `cv.location_id IS NOT NULL`, so `min_locations_for_tape_only` and `report fire-risk` are defeated for the affected units until someone notices. The remedy — `volume move L6-V1 --to bank`, which does restore "1 copies, 1 locations" — is an extra step no output, help text or doc mentions, and it has to be repeated after every reuse of that cartridge.
- **Fix:** Make binding the third writer of the pair it changes: in `bind_cartridge`'s transaction, when the bound cartridge has a non-NULL `location_id` and the volume's is NULL, `UPDATE volumes SET location_id = <cartridge's>` and insert the matching `volume_movements` row, exactly as `move_together` does (location.rs:340-348) — the volume is physically inside that cartridge, so this is recorded fact, not inference. If inheritance is deliberately not wanted, then ADR-0011:28-29 and :75-76 must be corrected and `volume init` must warn ("cartridge L6-0001 is at \"bank\"; this volume records no location — run `tapectl volume move`"), because silence is what makes the two columns disagree unnoticed.

#### [MEDIUM] compact-finish reverses a retired_permanent cartridge to pending_erase with no guard, no consent and no event — and mark-erased then runs with no gate at all

- **Evidence:** src/volume/write.rs:2462-2468, src/volume/write.rs:2357-2369, src/volume/write.rs:2470-2481, src/cli/operations.rs:342-394, src/cli/operations.rs:937-942, src/volume/binding.rs:177-188, docs/adr/0011-a-cartridge-place-is-a-location.md:57, src/cli/volume.rs:680, src/volume/write.rs:2170-2182
- **Claim:** `cartridges.status = 'pending_erase'` has two writers with different guards. `free_cartridge_if_last_live` (operations.rs:342-394), the ADR-0011 addition behind `volume retire`, requires the cartridge to be `in_use`, requires no other in-service volume on it, and logs a field-change event. `compact_finish`'s copy (write.rs:2462-2468) is a bare `UPDATE cartridges SET status = 'pending_erase' WHERE id IN (SELECT cartridge_id FROM cartridge_volumes WHERE volume_id = ?1 AND unmounted_at IS NULL)` — no status guard, no other-volume check, and no event (write.rs:2470-2481 logs the volume only). `compact_finish` also never gates on the source volume's own status: it SELECTs `status` at write.rs:2362-2368 and uses it solely as the event's `old_value`. So a cartridge the operator has condemned with `cartridge retire` — ADR-0011:57-58's "no amount of consent makes a medium you have declared unfit fit again", enforced at init by `refuse_retired` (binding.rs:177-188) — is silently returned to `pending_erase`. That matters twice over: `refuse_retired` no longer fires, and `cartridge mark-erased`'s ADR-0008 Tier-2 consent gate is conditional on `status != "pending_erase"` (operations.rs:937-942), so the escape ADR-0011 says is the operator saying they were wrong now runs with no prompt.
- **Failure:** Reproduced against the real deployed schema. `cartridge retire L6-0001 --reason "read errors" --yes` prints "Cartridge \"L6-0001\" retired permanently" / "`tapectl cartridge mark-erased L6-0001` is the only way back" and `cartridge list` shows `retired_permanent`. Running compact_finish's literal statement from write.rs:2462-2468 then reports changes()=1 and `cartridge list` shows `pending_erase`. `cartridge mark-erased L6-0001` next runs in a non-interactive session with NO consent prompt and prints "marked as erased (available for reuse)". Reachable in both orders, because `compact_read` (write.rs:2170-2182) SELECTs only `id FROM volumes WHERE label = ?1` and has no status gate: compact-read/compact-write, then retire the tape the read showed errors on, then compact-finish; or retire first and salvage afterwards. In the ordinary case compact-finish asks for no consent at all (the Tier-2 gate fires only when a unit would reach zero copies), and its output is the single line "compact-finish \"L\": volume retired" (cli/volume.rs:680), so the operator is never told the cartridge changed. Not a data-loss path: File 0 still refuses a sealed tape absolutely (write.rs:1569-1575), so reaching a WRITE on the condemned medium additionally requires the operator to physically bulk-erase it. What is lost is the Tier-2 declaration itself, its audit trail (no event row, so `report events --entity cartridge` shows the retirement and not the reversal), the `refuse_retired` warning at the next init, and the consent on mark-erased.
- **Fix:** Delete the second copy: have `compact_finish` call `crate::cli::operations::free_cartridge_if_last_live(&tx, vol_id)` — it already imports `retire_impacts` from that module for exactly this de-duplication reason (write.rs:2415) — so the `in_use` guard, the other-live-volume check and the event come with it, and print the same "Cartridge X is now pending_erase" line `volume retire` prints (operations.rs:305-309). At minimum add `AND status = 'in_use'` to write.rs:2464 so `retired_permanent` cannot be overwritten.

#### [MEDIUM] catalog rebuild asserts 'sealed' when it creates a volume row and asserts nothing when it finds one, so a rebuilt tape can be recorded as un-restorable

- **Evidence:** src/volume/rebuild.rs:614-637, src/volume/rebuild.rs:624, src/policy/coverage.rs:47-49, src/volume/session.rs:989, src/cli/operations.rs:1923-1927, src/volume/write.rs:283-285, src/cli/catalog.rs:495-512, src/volume/rebuild.rs:110-125
- **Claim:** `insert_all` resolves the volume row with `match existing_id(... SELECT id FROM volumes WHERE label = ?1)`: the `None` arm INSERTs with a hardcoded `'sealed'` (rebuild.rs:624), and the `Some(id)` arm (rebuild.rs:614-619) reuses the row verbatim and then hangs units, snapshots, stage sets, writes and positions off it. Same tape, same evidence, two different answers about its status, ten lines apart. The two other ways a volume row can exist both produce a non-sealed status: `volume_import` writes `'active'` (operations.rs:1923-1927) and `volume init` writes `'initialized'` (write.rs:283-285). `policy::coverage::eligible` is `status = 'sealed'` (coverage.rs:47-49), the only production writer of `'sealed'` is the seal path (session.rs:989), and `RebuildReport` carries only `volume_inserted: bool` (rebuild.rs:110-125) so the printed summary (catalog.rs:495-512) says nothing about the row it found.
- **Failure:** Measured. With a volume created by `tapectl import --label L6-IMP --media-type LTO-6 --capacity 2500G` and the rows `catalog rebuild --from-volume` would add for it (unit, current snapshot, stage set with origin='rebuilt', slice, completed write), `catalog locate legacy` prints Serviceable "NO" plus the note "L6-IMP cannot serve a restore in their current state (not sealed — retired, quarantined, erased, or still being written). Fetching one will not help." — a false statement about a tape the rebuild just read, since `restore` never filters on `volumes.status`. `report copies` prints "legacy: 0 copies, 0 locations [-]" and `audit` raises "[copy_count] legacy: has 0 copies, needs 2". Two realistic vehicles: the operator-guide DR recipe restores the heir kit database first and then rebuilds each tape (operator-guide.md:928-941), so a volume initialised before the kit snapshot and sealed after it comes back as `'initialized'`; and issue #136's `import`-then-rebuild pairing gives `'active'`. There is no repair: no command writes `'sealed'` outside the seal path, so the operator must hand-edit SQLite.
- **Fix:** Minimum, and all the code's own evidence supports: add a `volume_status_mismatch: Option<String>` to `RebuildReport`, set it in the `Some(id)` arm when the existing row's status is not `'sealed'`, and print one line — "note: L6-IMP was already in the catalog with status 'active'; a tape this command can rebuild is sealed, so this volume will not count as a copy and `catalog locate` will call it unserviceable". The consistent fix is to normalise the row to `'sealed'` in that arm, which inherits exactly the assumption rebuild.rs:624 already makes for a new row; note that `rebuild` never verifies a seal marker (no seal check exists in rebuild.rs), so if that assumption is too strong it is too strong in both arms and :624 is the one to change.

#### [MEDIUM] location info and location list never show cartridges, so the column ADR-0011 just gave a writer cannot be read from the location side

- **Evidence:** src/cli/location.rs:87-92, src/cli/location.rs:129-135, src/cli/location.rs:136-148, src/cli/cartridge.rs:36-41, docs/adr/0011-a-cartridge-place-is-a-location.md:19, src/cli/location.rs:319
- **Claim:** ADR-0011 made `cartridges.location_id` the single mechanism for where a cartridge is, and gave it a writer (`move_together`, location.rs:319) and two readers (`cartridge list`/`info`). The location-side views were not updated: `location list`'s query counts `volumes` and `volume_deposits` only (location.rs:89-92) and `LocationRow` has Name/Kind/Volumes/Deposits/Description columns (location.rs:43-56); `location info` lists volumes (location.rs:129-135) and deposits (location.rs:136-148) and nothing else. `cartridge list` has only `--status` (cartridge.rs:36-41), no `--location`, so there is no query anywhere that answers "what cartridges are at this location".
- **Failure:** Measured. After `location add bank` and `cartridge move L6-0001 --to bank` (which prints "cartridge \"L6-0001\" moved to \"bank\""), `location info bank` prints Kind/Description/Created and "Volumes: 0" with no mention of the cartridge, and `location list` shows bank with Volumes 0 / Deposits 0. An operator auditing a shelf or an offsite location — the question ADR-0011 exists to make answerable — gets an empty answer for every cartridge with no live volume on it (blank stock, `available` after mark-erased, `pending_erase` awaiting a bulk erase, `retired_permanent`), and for a written cartridge whose volume never inherited the location (see the binding finding) the location page is empty even though the tape is there. The only way to get the answer is to run `cartridge list` and read the Location column by eye.
- **Fix:** Add a cartridges count to `LocationRow` and its JSON (`SELECT COUNT(*) FROM cartridges c WHERE c.location_id = l.id`), and a Cartridges block to `location info` listing barcode + status + its current volume, alongside the existing Volumes and Deposits blocks. A `--location <NAME>` filter on `cartridge list` (the sibling of the existing `--status`) is the cheap half and can land first.
