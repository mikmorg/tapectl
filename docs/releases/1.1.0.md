# tapectl 1.1.0: release notes

What changed between `v1.0.6` and 1.1.0, for the person who runs tapectl. The record is
`git log v1.0.6..v1.1.0` (the merge commits name the batches), the issues closed from
2026-10-05 on, and ADR-0012's amendments of 2026-10-06, 2026-10-07 and 2026-10-12.

- **Status.** Frozen on master `4342589` (2026-10-12). It is not tagged yet: `v1.1.0` is
  tagged on the commit the real-drive proof on home2 passes on (`docs/handoff.md`). Until
  then, `tapectl --version` prints `1.1.0 (v1.0.6-…-g<sha>, <date>)`.
- **1.0.7 was never tagged.** Commit `a254c23` set the version to 1.0.7 (#399, #406, #407,
  #409, #417) and was never installed. Its changes are listed here with the rest.
- **home2 does not upgrade to 1.1.0. It starts fresh** (ADR-0012, 2026-10-12, items
  36–48). home2 runs 1.0.0 today. It gets a new catalog, created by `scripts/first-run.sh`
  from step 1. The escrow identity is kept, and every tenant key is new. So nothing below
  needs a migration rehearsal on home2. For a host coming from 1.0.0, the patch releases
  between 1.0.0 and 1.0.6 are listed at the end.
- **The minor version moved** because generated on-tape bytes changed (the version rule of
  2026-09-30). The on-tape authorization of 2026-10-07, which let agents re-pin the golden
  bytes, ends when v1.1.0 is installed (item 40). From then on, a failing
  `tests/on_tape_golden.rs` is again a CTO decision.

## On-tape format changes

The normative text is `docs/design/volume-format-v2.md`. `layout_version` stays 2 and the
magic stays `tapectl-volume-v2`. Every change below is additive under §1.2's rules.
`tests/on_tape_golden.rs` was re-pinned twice in this release, both times for RESTORE.sh.
The MANIFEST.toml pin did not move.

| Change | Ruling | Format doc | Golden re-pin |
|---|---|---|---|
| **The 1.1.0 heir path in RESTORE.sh and File 1.** RESTORE.sh reads the tape forward from one rewind: it keeps a cursor, checks it against `mt status`, and reads the seal last (#396). A non-empty `--to` is refused unless `--overwrite`, dar's "not restored" line is fatal, and the padding strip touches only trailing padding (#405). Slices stream through FIFOs into `dar --sequential-read -N`, using the envelope's isolated dar catalogue as `-A`. Where the dar is older than 2.7.21 and no matching catalogue exists, it **falls back to decrypting slices to scratch space on disk**, because dar 2.7.13 loses a file's tail when it streams without a catalogue. It also gains `--all`, a repeatable `--unit`, `--list` and `--path` (these two read the envelopes' dar catalogues, #418), and `--find-envelope` lists every envelope. A damaged envelope is told apart from a wrong key, `mt-st` is detected, and a dar that needs `gpg` is named before the tape is read (#412). `RECOVERY.md` and the system guide (File 1) read forward to match | 2026-10-06 items 2, 3, 18, 20, 21 | §6 | `bf895d0` (2026-10-06, CTO review) |
| **Forward compatibility.** File 0's `[volume]` and the seal marker's `[seal]` carry `requires = []`. Every reader, tapectl and RESTORE.sh alike, checks `magic`, `layout_version` and `requires`. It refuses a tape that needs a feature it does not know, by name, instead of misreading it. Readers find the seal by spacing to end of data and stepping back two filemarks, and use File 0's pointer only as a cross-check (#384) | 2026-10-06 item 15 | §1.2 | inside `bf895d0` |
| **A backup copy of every tenant envelope.** One `tenant_envelope_backup` per tenant, holding its primary's exact bytes, after the operator envelope pair and in the primaries' order. A reader opens the primary first and **turns to the backup only when the primary does not read, does not match its hash, or is damaged**. RESTORE.sh and `catalog rebuild` both do this (#418 item 2). The operator envelope has had its backup since v2's first write | 2026-10-12 item 44 (brought forward from 1.2.0, item 22) | §1.3 | `57f061f` (2026-10-12) |
| **The operator envelope's `catalog.db`, generation 3.** The per-file data follows the main catalog's narrow shape (`paths` + `file_versions`, as migration 030 made it), and records each entry's kind (dir, regular, symlink, special) and a symlink's target. A catalog rebuilt from a 1.1.0 tape keeps them. The file is about 22% smaller (12.2 MiB against 15.7 MiB per 100k files, #418's landing comment). This file is inside the encrypted operator envelope and is not golden-pinned. Its pins are fixtures written by the shipped generation-1 and generation-2 writers (`3439564`, `4342589`) | 2026-10-12 item 48 (#418 R3) | §1.4 | none (not a pinned file) |
| **How a data slice is made.** dar writes the archive to standard output (`dar -c - … --retry-on-change 0`). tapectl cuts the stream into dar slices framed exactly as dar frames its own, and age-encrypts each slice in memory, so the staging device never holds plaintext (#370). The slices are byte-compatible with `dar -t`/`-x`. The only on-tape difference is the recorded `dar_command` in MANIFEST.toml. dar now runs with `-N` everywhere, in tapectl and on the heir path (#412 item 9) | 2026-10-06 item 4 | §2 ("How a data slice is made") | none |
| **Slice size defaults to 1 GiB** (`slice_size = "1G"`, 10G before). The setting is per stage set, so existing sets keep theirs | 2026-10-06 item 10 | (config) | none |

**1.0.x tapes stay readable.** They do not carry `requires`, and an absent `requires` means
none (§1.2 rule 2). They carry no tenant backups, so a 1.1.0 reader reads their primaries
as before and has no second copy to turn to (§1.3, "Older tapes"). Their `catalog.db` is
generation 1 or 2, which `catalog rebuild` still reads by shape (§1.4). Every tape also
carries the RESTORE.sh of the tapectl that wrote it. In the other direction, a 1.0.x
RESTORE.sh ignores `tenant_envelope_backup` entries. A 1.0.x tapectl refuses a
generation-3 `catalog.db` (it finds no `files` table) rather than misreading it. After the
home2 fresh start no 1.0.x production tape remains: L6-0001, the only one, is erased and
reused (item 37).

## Catalog migrations 027–035

home2's 1.0.0 catalog stopped at 026. On the fresh start, all of these run on an empty
catalog at `init`. 027 and 028 had already shipped in 1.0.x patch releases. 029–035 are new
since v1.0.6. 034 and 035 were renumbered at integration, and their headers say so. A
migration file is now named for its position in `db::migrations()`, and a test refuses
one that is not.

## Changes an operator will notice

### Writing and confirming

- **One exit table for the write family** (#408; 2026-10-07 items 20, 32, 33). `volume
  write`, `volume resume`, `collection run`, `quick-archive`, `volume compact-write` and
  `volume compact` exit as follows:

  | Exit | Meaning |
  |---|---|
  | 0 | sealed and confirmed |
  | 2 | error, medium untouched |
  | 3 | confirm inconclusive |
  | 4 | interrupted, resumable with `volume resume` |
  | 5 | aborted, cannot resume |
  | 6 | medium proven bad, quarantined |
  | 75 | catalog busy before anything was written |

  `collection run` reports the worst outcome among its copies. A failure *after* a copy is
  sealed and confirmed exits 0, with a warning that names the command that finishes the
  step. The table is in `docs/troubleshooting.md`, "The write family".
- **`audit` exits 70 on an error**, so exit 2 only ever means violations (2026-10-07
  item 19). The scheduled-audit wrapper treats only 2 as VIOLATIONS.
- **The confirm is quick by default** (#387; 2026-10-06 item 1). After the seal, a write
  reads File 3 and then the seal marker. `--full-confirm` (on every command that writes a
  volume) opts in to the full readback. `collection run --full-confirm-first` reads back
  the run's first copy in full and confirms the others quickly (2026-10-07 item 31). A
  quick confirm is not a readback: verify freshness counts full sessions only, and
  `writes.write_verified` is set only by a full confirm or a passing full `volume verify`
  (#392). After each write, run `volume verify <label> --full` before `staging clean`.
- **Full readbacks keep checkpoints** (#410; migration 029). An interrupted full confirm or
  `volume verify --full` continues from where it stopped. It is dated from its oldest
  checkpoint, and a continuation older than the volume's `verify_interval_days` reads
  everything again (2026-10-07 items 1, 30).
- **A fill ceiling replaces the 50 MiB reserve and the 92% factor** (#391; 2026-10-06
  items 9, 16; 2026-10-07 item 3). Every write's pre-flight refuses a layout above 97% of
  the cartridge's capacity and names the overage. `--fill-ceiling` overrides it for one
  command on every write planned afresh (`volume write`, `collection run`,
  `quick-archive`, `volume compact`) and on `volume plan` and `collection plan`.
  `volume write`'s pre-flight and `cartridge info` print a worn-cartridge notice from the
  chip's lifetime attributes and the drive's counters (#299).
- **A unit larger than one cartridge is refused** at `stage create` and `collection plan`,
  with the limit for the generation. The check uses source size, before compression
  (#395; 2026-10-07 item 8).
- **Copy distinctness and `--policy-aware`** (#144; 2026-10-07 item 26). Two copies of one
  batch on volumes of the same cartridge are refused at plan time, and copies that share a
  location get a warning. `--policy-aware` (`volume plan`, `collection plan`, `collection
  run`) packs first the units whose findings a write would resolve.
- **Write and resume safety** (#400, #401, #403). An unreadable File 0 counts as blank
  only when the tape proves it. A File 0 read error with no blank evidence is refused, and
  `--force` is the override except on a cartridge the catalog binds to a live volume.
  Reads of File 0, File 3 and the seal are bounded. A new write session replaces an
  abandoned, unsealed one on the same volume. A resume continues from what the medium
  holds, not from the catalog's cursor alone. A source read or drive error mid-write
  interrupts the session (resumable) instead of aborting it.
- **`volume resume` adopts a volume the catalog lost mid-write** (#360; ADR-0012,
  2026-09-29 later amendment). A catalog restored from a backup taken between `volume
  init` and `volume write` no longer leaves that volume `initialized` forever. The resume
  adopts it only when all four of these hold:
  - the File 0 uuid matches;
  - a seal marker binds the front index;
  - a passing full verify is recorded after the rebuild;
  - the front-index hashes equal the catalog's own staged hashes.
- **Signals** (#404). SIGTERM and SIGHUP are handled, long loops stop at safe points, and
  dar dies with tapectl instead of being orphaned.

### Staging

- **No plaintext on the staging device** (#370) and **the source is read once** (#364),
  hashed beside dar's read and tied to it by stat checks. A file that changes during
  staging refuses the stage (dar's retry-on-change is off). The write's `catalog.db` is
  built in the home, and `read-slices` directories are named by unit uuid.
- **One isolated dar catalogue per stage set**, made by its own dar run (#419).
- **`stage create --jobs N`** and `collection run --jobs N` stage several units at once,
  largest first (#368; `[staging] jobs`, default 1). `[staging] hash_threads` (default 1)
  hashes several source files at once (#366). Both defaults stay at 1 until the home2
  measurements are in (2026-10-07 item 12).
- **Staging integrity** (#402). `staging clean` is atomic, and an incomplete staged set is
  refused before the tape is touched. Each encrypted slice is fsynced before it is
  recorded (#409, the fsync part). A failed stage still starts over (#409 stays open,
  2026-10-07 item 11).
- **The unit's own `.tapectl-unit.toml` is not content** (#378; 2026-10-07 item 24). `unit
  tag`, `unit rename`, a `[policy]` edit, or a changed `compression` or `slice_size` mints
  no version. `collection sync` and `unit discover` refuse two directories that carry one
  uuid.

### Restoring

- **`tapectl restore volume <label> --to DIR [--unit …]`** restores several units from one
  volume in one forward pass, each into `DIR/<unit>` (#398). `--spool` forces the
  decrypt-to-disk path on `restore unit` and `restore volume`.
- **Restores stream decrypted slices into dar** (`--sequential-read`), and `restore file`
  reads only the slices that hold the file (#411). The plaintext sha256 is no longer
  re-checked after decryption (2026-10-06 item 23).
- **Restores check space, the destination and `--file` before touching the tape**, and
  scratch space is never in `$TMPDIR` (#406). The new flags `--scratch`, `--overwrite`
  and `--no-space-check` are on `restore unit`, `restore file` and `restore volume`.
- **Tape reads open read-only where they can.** `volume verify`, and a resume that only
  re-confirms, open the drive read-only, so a write-protected sealed tape can be verified
  (#407).

### Policy and audit

- **The tape-only multiplier raises copy floors only** (#423 part 2; 2026-10-12 items 43,
  46, 47; 2026-10-07 items 15, 34). A tape-only unit needs `min_copies` × the multiplier
  copies, and each name in `required_locations` takes the multiplier too. The
  distinct-location count `min_locations` is not multiplied. At the defaults that is 4
  copies in 2 places, where `snapshot mark-reclaimable` used to demand 4 places. `audit`,
  `unit mark-tape-only`, `snapshot mark-reclaimable` and `report supersedable` share one
  rule in `policy::coverage`. A tape-only shortfall is a consent gate (ADR-0008 Tier 2): it
  is listed, a terminal asks, and `--yes`/`--force` proceed. See #425 under open items for
  where `min_locations` is still not enforced.
- **New `audit` checks**: `tenancy`, which is advisory and names a unit whose catalog
  tenant disagrees with its dotfile or with the recipient lists of its written copies
  (#383); `tape_alert`, a
  warning for a raised TapeAlert on a live volume's cartridge, answered only by a full
  verify that started after it was logged (#308, #303); and `read_error_trend`, which
  flags a cartridge whose corrected read errors per GiB climb (#421). A rise counts only
  above 1 per GiB and beyond `[health] read_error_rise_factor` times the previous reading
  (2026-10-07 item 7).
- **`tenant reassign`** shows the copies the destination tenant cannot open, and rewrites
  the units' dotfiles (#383).
- **`volume verify --full` records a sealed copy's missing write figures** after the fact
  (#423 part 1).
- **`archive-set create/edit/sync` refuse `verify_interval_days` below 1** (#422), and so
  do loading config.toml and `config check`.

### Drive health and forensics

- **`tapectl drive poll`** reads the drive's health pages, and the chip when a cartridge is
  loaded, through the SCSI generic node only. It never opens the tape node and never moves
  the tape. Everything it reads is journalled. A raised TapeAlert or a drive-reported
  unrecovered error exits 1, and it exits 75 without reading when a tapectl command holds
  the drive (#309; 2026-10-07 item 29). `scripts/install-systemd.sh` installs
  `tapectl-drive-poll.timer`, daily at 06:30, beside the audit (Monday 09:00) and the
  catalog backup (daily 03:00).
- **`report cartridge-health`** ranks every cartridge, worst first, with the reasons.
  `cartridge info` shows the last bind, the last contact and both mount dates (#307).
- **TapeAlert flags are decoded** by parameter code from the journalled bytes (#303). `parse_mam` keeps
  the chip's lifetime attributes (#299). `catalog rebuild` dates a tape by its own File 0
  and seal marker (#305).
- **`report health --json` is an object**, `{readings, read_error_trends,
  read_error_rise_factor}`, no longer a bare array (2026-10-07 item 21).
- **The journals are never pruned** (#310; 2026-10-07 items 13, 28). `db stats` reports
  each table's rows and size and the journals' growth over the trailing 90 days. `db
  backup` prints what it copied.

### Operating and installing

- **`tapectl status`** shows what is running and how the last sessions ended, read from
  the session logs alone. It opens no catalog and no config. With `[ops] group` set, every
  command run as the service user keeps the home 0710 and `logs/` 2750 owned by that
  group, so a member can run `tapectl --home <tapectl home> status` without sudo and can
  open nothing else in the home (#393). home2's profile sets `OPS_GROUP=tapectl-ops`
  (2026-10-07 item 18). `first-run.sh` step 7 also grants the group traverse (`x` only) on
  each directory above the home that lacks it (on home2, `/srv/archive_meta` is root 0750),
  then checks `status` as the operator with the group instead of assuming it works;
  `scripts/first-run-reentry-mhvtl.sh` proves it on mhvtl, with a control that the same read
  fails without the group.
- **`tapectl config set`, `config add` and `config remove`** edit config.toml in place.
  They keep its comments, refuse an unknown key by name, validate the result as `config
  check` would, and replace the file atomically (#143; 2026-10-07 item 27).
- **Adopting an existing age keypair** (#424; 2026-10-12 item 42). `init --operator-key
  <file>` and `tenant add --adopt-key <file>` register a key that someone already holds
  instead of minting one. `key import` stays public-keys-only. In `first-run.sh`,
  `ADOPT_KEYS_FROM` (`--adopt-keys-from`) points at a directory of `<name>.key` files. The
  copy-out from an old home is runbook F in `docs/keys-and-recovery.md`.
- **`first-run.sh` adopts the original escrow identity** through `ESCROW_PUBLIC_KEY` in a
  profile, or `--escrow-public-key`, at step 7, under `--auto` too (`9c3a36f`; item 39).
- **`first-run.sh` step 13 can be re-entered** after an interrupted write (#414). It finds
  the volume's state and continues: the write, a `volume resume`, or only the post-write
  steps for a sealed volume.

## From 1.0.0 to 1.0.6, in brief

For a host coming from 1.0.0. None of these changed on-tape bytes.

- **1.0.1**: sha2's assembly backend (#365).
- **1.0.2**: a write session holds a per-volume flock, and the catalog has a busy policy
  with exit 75 (#376, #377). Migration 027, and snapshots in one transaction
  (#372–#374).
- **1.0.3**: the pre-write full hash is off by default. `--prewrite-hash` restores it.
- **1.0.4**: progress output, phase timings (migration 028) and a session log per long
  operation under `<home>/logs/` (#386).
- **1.0.5**: tape reads move forward instead of rewinding before every file (#389).
- **1.0.6**: the staged-file read, the inline hash and the tape write overlap, and tape
  reads run ahead of the hash (#390).
