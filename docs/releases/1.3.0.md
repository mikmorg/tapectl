# tapectl 1.3.0: release notes

What changed between `v1.2.0` and 1.3.0, for the person who runs tapectl. The record is
`git log v1.2.0..` on the 1.3.0 tree, issues #418 (R4), #476, #477 and #480, and ADR-0012's
amendments of 2026-10-16 (evening) to 2026-10-19 (items 76–103).

- **The cross-volume index.** Until now each tape described only itself: no tape said where a
  unit's other copies or older versions were. A tape written by 1.3.0 carries an index of the
  archive as the catalog knew it when the tape was written (`volume-format-v2.md` §1.5, items
  78–80, 103): which volumes hold which version of each unit, and, for a tenant, every path
  with its size and recorded sha256.
- **Restore repairs what it can** (#480, items 101–102). A slice damaged on one cartridge is
  read from another copy; files still damaged are filled from another copy of the same version;
  what no copy can give costs only its 64 KiB chunks. RESTORE.sh does the same on the heir path
  as far as the `age` program allows, and checks every restored file against its recorded
  sha256 (item 103).
- **A re-pin release.** Generated on-tape text and envelope members changed: RESTORE.sh, File 1,
  RECOVERY.md and the new `index/` members. The CTO approved the re-pin and its contents (items
  81, 101–103). File 0, the front index, the seal marker, MANIFEST.toml, the on-tape `catalog.db`
  and the slices are written as 1.2.0 writes them.
- **Every Rust reader of a tape checks its `requires` list** (#476), before reading content.
- **No catalog migration.** The catalog stays at schema 036.
- **Spanning is designed, not built.** The CTO ruled it on 2026-10-16/17 (items 76–77, 82–100):
  spannable units, opt-in per unit, packed last and cut at the drive's early warning, then the
  short seal. It is built right after #420's short seal (#478), which needs a real-drive
  measurement first.
- **Issues this release finishes:** #418, #476, #477, #480, and #482's code (its real-drive LTO-5 check stays open).

## On-tape changes

**New envelope members** (§1.5). Each tenant envelope (and its byte-copied backup) gains
`index/units.tsv` (that tenant's units: each version, its slice range, and every volume holding
it, by label, uuid, chip serial, generation, state and seal time) and `index/paths.tsv` (each path
of those versions with its kind, size and recorded sha256). The operator envelope gains
`index/units.tsv` across every tenant, with no paths. Tab-separated text with four escapes, a
header line naming the columns, readable with awk and grep. The index lists every current version
with a live copy, plus the versions the write itself carries (item 80). It is as of its own
tape's write: the newest tape's index is the most complete. It needs no `requires` entry: an
older reader ignores envelope members it does not know.

**RESTORE.sh:**
- `--where UNIT` lists every version of a unit and the tapes holding it; `--find TEXT` finds a
  path and the tapes holding its version. Both read the index of the envelopes the key opens.
- A slice that fails its checksum is taken from another copy matched by its sha256 alone: a
  directory of slice files (`--slices-from DIR`) or a second tape (`--swap-tapes`). Either option
  restores slice by slice onto disk, about twice the unit's size.
- After every restore and fill, each restored regular file is checked with `sha256sum` against
  the index (`--no-file-check` skips it). dar's own per-file check is a short checksum where two
  equal byte flips can cancel; the recorded sha256 is not.
- A file that could not be restored, or fails its check, is listed in
  `.tapectl-damaged-files.txt` in the unit's directory, and the run ends `RESTORE INCOMPLETE`
  (exit 1); `--fill-from LIST` against another tape of the same unit and version restores only
  those files. Another version is never used.
- `RESTORE COMPLETE` is printed only when nothing came back short.

**File 1** was rewritten for #477's eleven findings and a fresh reader's thirteen more: a
glossary and one key placeholder, the non-rewinding device and `TAPE_DEVICE` as an environment
prefix, commands for every manual step (with the file spacing done right), the UNSEALED and
DAMAGED cases, a completeness check for whole, `--path` and `--all` restores, the whole box (which
tape first, `--where` per unit, one directory per unit, when to stop), loading a tape and a drive
that does not show up, hardware, key files, and rung 3's stopping point. **RECOVERY.md** gains a
section on the index and one on damaged slices and files.

**Two fixed points** (item 81). RESTORE.sh's "this tape needs tapectl ≥ …" text stays "tapectl
1.1.0", and `requires` stays empty, so a 1.1.x or 1.2.0 RESTORE.sh reads a 1.3.0 tape (it ignores
the index) and a 1.3.0 RESTORE.sh reads an older tape (`--where` and `--find` say it has no index).

**The golden pin moved** four times in 1.3.0's commits, each in its own commit naming old and
new: from 1.2.0's `6c7bb948…` through `36c970aa…` (the index modes and File 1) and `594da829…`
(slice replacement and the damaged-file list) to `072b0c6e…` (the per-file sha256 check).
MANIFEST.toml's pin did not move.

## tapectl changes

- **`volume init` says what it took the cartridge for** (#482): a last line such as `medium:
  LTO-5, 1.50 TB (the cartridge chip's medium density code 0x58)`, naming what decided the
  generation and the capacity (`medium` in `--json`; the same line follows `volume write
  --init`, on stderr). `volume list` gains GENERATION and CAPACITY columns (`media_type`,
  `capacity_bytes` in `--json`). Verified on mhvtl: an LTO-6 drive takes LTO-5 and LTO-6
  cartridges through init, write, verify, restore and the heir path with no extra flags; the
  HP drive with a real LTO-5 cartridge is the operator's check on #482.
- **`volume plan`** prints an estimate of the index's size (`index_bytes`, `index_bytes_on_tape`
  in `--json`).
- **`catalog rebuild --from-volume`** reads the operator envelope's index and lists the volumes it
  names that the catalog lacks, as a to-do list for disaster recovery (`cross_volume_index` in
  `--json`). It never creates a row from it.
- **`restore unit`, `restore file` and `restore volume` repair** (#480). A slice that fails its
  checksum is read from another cartridge holding the same slice: tapectl asks for it by label,
  sticker and chip serial, resumes where the first stopped, and keeps it in the drive while it
  serves; with no terminal it refuses and lists the holders. Files still damaged or missing are
  restored from another copy of the same version (a different staging), each checked against the
  version's recorded sha256. What no copy can give is written as zeros chunk by chunk (no
  unauthenticated byte is ever written), and the restore ends INCOMPLETE (exit 2), naming the
  slice, its byte ranges and the files. A slice assembled from more than one source is checked end
  to end against its recorded plaintext sha256 before it counts as whole. `--json` carries
  `substitutions` and `filled`.
- **Every Rust reader that takes File 0 refuses a tape whose `requires` it does not know** (#476):
  `restore unit|file|volume`, `volume verify` (exit 3, nothing recorded), `volume read-slices`,
  `volume compact-read`, `volume compact` and `volume resume`'s adoption of a lost write, as
  `restore raw-volume` and `catalog rebuild` already did.

## Tooling (not in the binary)

- **`scripts/lto6-fill.sh`** measures what the drive does after early warning (#420): one 1 GiB
  slice past the first refusal, a filemark and a seal-sized block, a read-back by LOCATE, and the
  room from early warning to the hard end (item 100). It is the operator's run on home2.
- **`tests/performance.rs` `perf_staging_throughput_per_pass`** (#364): staging per pass on a 4 GiB
  fixture, v1.0.0 to v1.2.0 recorded in `docs/perf-baselines.md`.

## Catalog migrations

None. The catalog stays at schema 036, as at `v1.1.1`.

## Testing

The mhvtl gate has 47 legs: four new heir legs run the tape's own RESTORE.sh with the real
`age`, `dar`, `mt`, `tar` and `sha256sum` against tapes tapectl wrote: `heir_where`, `heir_find`,
`heir_slice_from_copy` (a second real cartridge, one slice of the first made bad as it is read,
replaced from a directory of slice files copied off the second) and `heir_file_check`. They are
the only real-tool test of these features (ADR-0012 item 70). A crypto review of the
chunk-by-chunk decryptor behind tapectl's chunk salvage found it correct and one unsafe use,
fixed before release: a slice whose ciphertext hash did not match is whole only if its plaintext
proves it, and chunks of two different age files are never mixed into one slice.

## Costs

`catalog_budget` gains `IndexBuild`: two statements plus one per listed version, none per path. A
clean restore's tape motions and statements are unchanged; a restore that swaps a cartridge costs
one load and one contact per swap.

## Upgrading

home2 runs 1.1.0 and upgrades in place, straight to 1.3.0 (`docs/handoff.md`, (f)). 1.3.0
contains 1.1.1, 1.1.2 and 1.2.0; read their notes (`docs/releases/1.1.1.md`, `1.1.2.md`,
`1.2.0.md`), not restated here.

1. **Back up the catalog first, with the old binary:** `tapectl-op db backup --to <path>` with
   1.1.0 still installed. Migration 036 (from 1.1.1) is the only one the upgrade applies.
2. **Tapes written before the upgrade are not touched.** New writes carry the index and the 1.3.0
   text. The first tape 1.3.0 writes is the first whose `--where` lists the earlier tapes.
3. **ADR-0012 items 72 and 81: the on-tape authorizations of 1.2.0 and 1.3.0 end when v1.3.0 is
   installed.** After that, a failing `tests/on_tape_golden.rs` is a CTO decision.
4. **The step-12 rehearsal** proves the new binary on the HP drive before the next write, and is
   the first real-tool run of RESTORE.sh's `--where`, `--find` and repairs there.
