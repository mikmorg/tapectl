# tapectl 1.4.0: release notes

What changed between `v1.3.0` and 1.4.0, for the person who runs tapectl. The record is
`git log v1.3.0..` on the 1.4.0 tree, issues #479, #481 and #483, and ADR-0012 items 105–107.

- **File 1, a re-pin release.** File 1 and RECOVERY.md were rewritten for a third and a fourth
  fresh read of the guide (#481, item 105). RESTORE.sh, MANIFEST.toml, File 0, the front index,
  the seal, the envelopes and the index are written as 1.3.0 writes them; no golden pin moved.
- **`volume rewrite` compacts a tape in place** on its own cartridge, even when it holds the only
  copy of a unit, behind a typed consent and a full readback (#483, item 106).
- **tapectl's restore takes `--key FILE`**, so an heir holding only the escrow secret restores
  through tapectl, with its chunk salvage and file fill (item 107).
- **A profiling toolkit** measures a drive and emits its `[[backends.lto]]` block (#479, items
  96–98, 100), and a new `post_warning_bytes` key caps the slice size.
- **One catalog migration**, 037 (`volume rewrite`'s pending record).
- **Issues this release finishes:** #479 (its real-drive run stays the operator's), #481, #483.

## On-tape changes

**File 1** gained: "The Heir Kit's catalogue" (opening `catalog.db.age` with the escrow key, as of
the day the kit was made, with two `sqlite3` queries); "tapectl itself" (the public repository
https://github.com/mikmorg/tapectl beside File 0's `tapectl_version`, building it, and the escrow
heir's three commands: `init` with the escrow public key, `catalog rebuild --from-volume --key`,
`restore unit --key`); telling a bad key file from a tape of another installation; "A renamed unit"
and "Two units of one name" (a directory per unit uuid where a name recurs across tapes); "When no
envelope reads"; package names with one `apt` line and the oldest `age` tried (1.0.0-rc.1, with
age's release page); IR and IT firmware defined; internal and external drives, USB and Thunderbolt;
the disk chosen after the units are listed, on a Linux filesystem, with one disk-space rule; a
manual slice step that stops on a failed hash; and `truncate` in the manual tool list. After a
fifth fresh read (an heir holding only the escrow key; verdict "mostly", one serious finding),
"Did the restore get everything?" gained a fourth check: after `--all`, every unit
`--find-envelope` lists is in the destination, because with the operator envelope unreadable
`--all` restores one tenant's units and the other checks still pass. That read also fixed the
script's name in step 4, `$TMPDIR` before the first listing, `age-keygen -y` for the escrow
public key without a cover sheet, `--where` needing a 1.3.0 or newer script, where `--all` stops
after a failed slice, and the disk room for slices kept beside restored files. Its other minor
findings are #485. **RECOVERY.md** repeats the parts that concern one envelope.

**Fixed points.** RESTORE.sh's "this tape needs tapectl" text stays "tapectl 1.1.0" and `requires`
stays empty, so 1.x tapes read each other's.

## tapectl changes

- **`volume rewrite SOURCE --label NEW`** reads the source's live slices into staging, re-reads
  each from the staging disk against its hash, builds the new volume's real layout and checks it
  fits, retires the source, erases its cartridge, initialises NEW on the same cartridge, and writes
  the slices with the full confirm before releasing staging. Consent: the usual Tier-2 question when
  every live slice has a copy elsewhere; when some live slice has none, the source's label typed at
  a terminal or `--only-copy-on-staging LABEL` (`--yes` does not give it; the command has no
  `--force`). From the erase until NEW passes its full readback the staging disk holds the only copy
  of those units; nothing releases those slices in that window (`staging clean --force`, the release
  after `volume write`/`volume resume`, `collection run`), and `volume rewrite --resume NEW` finishes
  a rewrite that stopped. `--dry-run` shows the plan and the consent it needs. Every other retire
  path keeps the absolute zero floor. Events `rewrite_*`; operation `volume rewrite`.
- **`report compaction-candidates --plan [--generation LTO-N]`** groups candidates whose live data
  fits one destination tape, largest reclaim first, and names the commands.
- **`--key FILE`** (repeatable) on `restore unit`, `restore file`, `restore volume` and `catalog
  rebuild`: an age identity file used for that command only, never copied into the home, registered
  or logged; refused by name before the drive opens when it is not an identity.
- **`[[backends.lto]] post_warning_bytes`** (decimal): the measured room from the drive's early
  warning to the hard end. With it set, a slice plus the seal must fit in half the smallest such
  room: `config check` reports a `slice_size` that does not (exit non-zero), `config set` refuses
  an edit that breaks it, and `stage create` refuses; every other command still loads the file.
- **Over a damaged slice, `restore` no longer calls dar's own files stale copies** of an earlier
  restore and no longer says to empty the destination; it names them as dar's partial output
  (#484; message only).

## Tooling (not in the binary)

- **`scripts/lto-profile.sh`** (`docs/lto-profiling.md`): on a named test cartridge, the
  measurement set of the old `lto6-measure.sh` plus the past-early-warning fill to the hard end,
  a report with every figure's source and the cartridge's wear beside its end-of-tape point, and
  `--emit RUN_DIR...` for the drive's `[[backends.lto]]` block (`fill_ceiling` never above 0.97;
  `post_warning_bytes` the smallest measured room). `scripts/lto6-fill.sh` and
  `scripts/lto6-measure.sh` remain as thin wrappers; consent is by the medium serial only.
- mhvtl refuses writes at its cartridge size and then alternates refusing and accepting, keeping no
  data past the first refusal; the profiling report marks an emulated drive and `--emit` ignores it.

## Catalog migrations

**037** adds `pending_rewrites` and `pending_rewrite_sets` (`volume rewrite`'s record). It is
applied the first time 1.4.0 opens the catalog. There is no downgrade past it: a 1.3.0 or older
binary refuses a catalog ahead of its migration list.

## Upgrading

home2 runs 1.1.0 and upgrades in place, straight to 1.4.0 (`docs/handoff.md`, (f)). 1.4.0
contains 1.1.1, 1.1.2, 1.2.0 and 1.3.0; read their notes, not restated here. Migrations 036 (1.1.1)
and 037 apply on the first open.

1. **Back up the catalog first, with the old binary:** `tapectl-op db backup --to <path>`.
2. **Tapes written before the upgrade are not touched.** New writes carry 1.4.0's File 1 and
   1.3.0's index.
3. **The on-tape authorizations of 1.2.0, 1.3.0 and 1.4.0 end when v1.4.0 is installed** (ADR-0012
   items 72, 81, 104, 105). After that a failing `tests/on_tape_golden.rs` is a CTO decision.
4. **The step-12 rehearsal** proves the new binary on the HP drive before the next write.
