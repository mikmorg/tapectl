# tapectl 1.7.2: release notes

What changed between 1.7.1 and 1.7.2, for the person who runs tapectl. The record is
`git log v1.7.1..` on the 1.7.2 tree, issues #388, #496 and #498 (tapectl's half), and ADR-0012 items 161-166, 174, 175 and 180, ruled 2026-10-25 to 2026-10-27.
No byte that tapectl writes to tape changed, so by the version rule this is a patch.

- **Logical Block Protection** (#388, items 161-166). tapectl arms the drive's Logical Block
  Protection for every open of the drive it makes and clears it before it lets the drive go.
  Every block it writes carries a Reed-Solomon CRC that the drive checks before it writes the
  block, and every block it reads comes with the drive's CRC, which tapectl checks. This closes
  the hop the default quick confirm leaves open: damage between tapectl and the drive while the
  tape is written.
- **The quick confirm stays the default** (item 161). LBP does not read the cartridge back, so
  `no_full_verify` still names a volume until its first full readback, and `--full-confirm`
  and `volume verify` are unchanged.
- **A drive or host that cannot take it is warned about once and written without it**
  (item 165): the write is as strong as one by 1.7.1, and the catalog records that LBP did not
  run, and why.
- **A block the drive refuses is written again, once per run** (items 166 and 174). tapectl
  goes back to the start of the file that holds the first block the drive did not accept and
  writes on from there. A second refusal in the same run leaves the session `interrupted`
  (exit 4) for `volume resume`, which gets one retry of its own. Item 174 replaced item 166's
  abort on the first refusal with this retry.
- **A page left armed by a crash is cleared at the next open**, with a note (item 164);
  `drive status` shows it, and the Heir Kit's cover sheet says a power cycle clears it.
- **`volume info`, `report verify-status` and `drive status` say what ran** (item 165), in
  text and `--json`.
- **#496:** `volume verify`'s progress line has a total.
- **#498, tapectl's half** (item 180): a streamed restore feeds dar one stream on its standard
  input, the slices joined back into the stream dar wrote, instead of a named pipe per slice, so
  dar's fault with piped slices cannot reach it. RESTORE.sh changes in 1.8.0 (item 181).
- **Each line is told once:** the early warning's first refused block, the test hook's
  announcement, the per-file count of refusals and the short ending's report reached stderr or
  the session log twice since 1.6.0. Each now goes once to each place it belongs, like every LBP
  line.
- **One catalog migration, 041.**
- **Issues this release finishes:** #496; #388 once the real-drive acceptance passes. #498 stays
  open for RESTORE.sh's half (1.8.0).

## On-tape changes

None. No golden pin moved (`cargo test --test on_tape_golden` passes on 1.7.1's pins): RESTORE.sh,
MANIFEST.toml, the short seal, File 0, File 1, the front index, the seal and the envelopes are
1.7.1's, and `requires` is computed as in 1.7.1. The CRC travels between tapectl and the drive
only: the drive checks it and writes the 524,288-byte block alone, so a tape written with LBP
reads like any other, by RESTORE.sh, `dd`, a 1.7.1 tapectl and the heir's tools. A 1.7.1 reader
reads every tape 1.7.2 writes, and the other way round.

The operator envelope's `catalog.db` keeps generation 3's shape: it has no `volumes` table, so it
carries neither new column. Its `user_version` mirrors the catalog's schema level, so it reads 41
where 1.7.1 wrote 40. No golden pin covers it, as for 38 to 40.

## Logical Block Protection (#388)

**What is armed** (items 162, 163). The drive's Control Data Protection mode page (0Ah/F0h),
method 01h (Reed-Solomon, which LTO-5 and later accept), with LBP_W and LBP_R. tapectl reads the
page with `sg_modes` and sets it with `sg_wr_mode`, both from sg3-utils, on the SCSI generic node
the kernel binds to the tape node (never config's `device_sg`). The SG boundary grows by exactly
that one MODE SELECT and the MODE SENSE that checks it (`docs/design/threat-model.md` §2;
`tests/sg_boundary.rs` pins both). While the page is armed, st carries 524,292 bytes per block:
the format's 512 KiB and the 4-byte CRC.

**Its life** (item 164). An open arms the page inside st's exclusive open, so nothing else does
data I/O on the drive while it is armed:
- the open rewinds, reads the page (one already armed is a leftover), sets it, reads it back,
  sets st's block size and sends one probe read of a 524,292-byte block at BOT. A host path that
  cannot carry a block that large answers without sending it, and the open falls back;
- the close writes the filemark st's own close would after a block write, while the page that
  protected the blocks is still armed, then puts the page back as found (a leftover is cleared,
  never restored), reads it back and sets st back to 524,288 bytes;
- a page a crash left armed (SIGKILL, a second Ctrl-C, a power loss) is found by the next
  tapectl open, which says so and clears it. Until then other programs' reads of the drive
  (RESTORE.sh, `dd`) fail with I/O errors, never wrong data, and a power cycle clears it too.
  RESTORE.sh does not change, and sg3-utils stays off the heir's path.

**Which reads are checked** (item 175). This build arms LBP_R for every read tapectl makes:
writes' confirms, `volume verify`, restores and the other readers (`tape::lbp::LBP_R_POLICY =
AllReads`, item 162). The build also carries item 175's fallback, LBP_R only for the confirm of a
session that wrote with LBP, for a drive that returns no valid CRC for blocks written without
LBP; step 1 of the real-drive acceptance (R1) decides which one ships (below). A read whose CRC
does not match is a read error, inconclusive (`volume verify` exits 3), never a quarantine.

**When it cannot be armed** (item 165). A drive without LBP, no sg node bound, no `sg_modes` or
`sg_wr_mode`, an sg node the user cannot open for writing, a page that will not take, or an st or
HBA that cannot carry 524,292 bytes in one command: a write prints one warning per drive per
command and writes without it, as strong as a write by 1.7.1:

```text
warning: Logical Block Protection is not available on <device>: <why>. tapectl writes without it; the write is
as strong as one by tapectl 1.7.1 (its sha256 checks are unchanged), and the catalog records that LBP did not run.
```

A read that cannot arm it says so in the session log only. No config key turns LBP off. The user
tapectl runs as needs read-write on the drive's sg node; on home2 the tape group has it.

**When the drive refuses a block** (items 166, 174). With LBP armed, a write `EIO` is how the drive
refuses a block whose CRC did not match the bytes it received, and st cannot tell that from
another write error, so every one is treated as a refusal. tapectl reads the drive's position
(READ POSITION), finds the planned file holding the first block the drive did not accept, returns
to that file's start and writes on from there, from staging, with fresh hashes and CRCs. Every
re-sent block is checked by the drive again. The session log and stderr carry one line, and the
catalog a `write_lbp_retry` event:

```text
the drive refused a write with Logical Block Protection armed in tape file <n>; its position (logical object
<lba>) is in tape file <m>: writing on again from the start of tape file <m>, once (ADR-0012 item 174)
```

**One retry per run.** A second refusal in the same run is not retried: the write stops with the
tape unsealed, nothing on it counted, and the session `interrupted` (exit 4), not aborted. The
error names the second refusal and says to check the host-to-drive path (the HBA, the SAS cable
and its connectors, the drive) before `tapectl volume resume <label>`. A resume is a new run, so
it gets one retry of its own (item 174's applied reading, ratified 2026-10-26). A refusal tapectl
cannot place from the drive's position is not retried at all and stops the run the same way. A
refusal of `cartridge erase`'s filemark is an erase that failed part-way (exit 4), as any is.
The kernel log names a refusal "logical block guard check failed".

**What the catalog records** (migration 041). `volumes.write_lbp` is `on` when every run of the
volume's write session wrote with LBP, `off` when none did (with the reason in
`write_lbp_note`), `mixed` when the runs differed (with why a run lacked it), and NULL for
a volume written before 1.7.2, rebuilt from tape (the tape does not say) or not written yet. A
resume with LBP of a session an older tapectl began and wrote part of is `mixed` (that run wrote
without it). A change writes a `write_lbp` event.
`no_full_verify` stays the one audit finding: LBP is write-time evidence of its own and never
rides on `verification_sessions`.

**What the operator sees:**
- `volume info`'s "Write check" line: `Logical Block Protection on every block (the drive checked
  tapectl's CRC)`; `none (Logical Block Protection did not run: <why>); as strong as a write by
  tapectl 1.7.1`; `Logical Block Protection on part of the write (<why>)`; `not recorded (written
  before tapectl 1.7.2, or rebuilt from tape, which does not say)`; `none yet (no write
  recorded)`.
- `report verify-status` ends each row with `write check: LBP`, `no LBP (<why>)`, `LBP on part
  (<why>)` or `not recorded`.
- `drive status`: `LBP page:  not armed (<sg>)`, or `LBP page:  ARMED (<sg>), and no program has
  the tape node open: …` for a leftover, with what it does to other readers and what clears it.
  When a tapectl command takes the drive between the node's answer and the page's read, the page
  is not reported and a note says why.
- The session log names the page armed on each open: `Logical Block Protection armed on <device>
  (<sg>): the drive checks tapectl's CRC on every block written, and sends its own with every
  block read`.
- Each LBP line meant for the operator is printed once on stderr and written once in the session
  log; a read open's note and the "armed" line go to the session log alone.
- The Heir Kit's cover sheet: "If every read of a tape fails with an I/O error, and tapectl crashed
  or was killed on that machine just before, switch the tape drive off and on, then try again."

`docs/troubleshooting.md` has an entry for each message, with its fix.

**The test hook** `TAPECTL_TEST_LBP_CORRUPT_BLOCK=n1[,n2…]`: each listed block write since the
write store opened (counted from 1, re-sent blocks too) goes to the drive with one bit of its CRC
flipped, so the drive refuses it as it refuses a block damaged on the way. It changes no byte of
the data, is refused with the open failing when the open did not arm LBP for writes, and is
announced on stderr and in the session log before the first byte. It is how the gate and the
real-drive acceptance provoke a refusal. Never set it for a real write.

## #496: `volume verify` shows a total

`volume verify`'s progress line had no total, because the Layout a verify rebuilds from the
front index never sizes the seal. The readback's bytes are now one sum, the files the Layout
sizes plus the seal when its size is known, and the read-error rates' denominator (#495) is that
same value.

## JSON keys added

All are additive. Nothing a 1.7.1 script reads was removed or changed.

| Command | Keys |
|---|---|
| `volume info` | `write_lbp` (`on`, `off`, `mixed` or null), `write_lbp_note` (null when `on` or not recorded) |
| `report verify-status` | each element: `write_lbp`, `write_lbp_note` |
| `drive status` | `drive.lbp_page`: `{"node", "armed"}`, or null when the page was not read |
| `report events` | new actions on a volume: `write_lbp` (field `write_lbp`, the old and new word, the note as `details`) and `write_lbp_retry` (field `from`, the tape file written again from; `details` `{"refused_in", "position", "from"}`) |

## Catalog migration 041

Two nullable columns on `volumes`, added in place: `write_lbp` (TEXT, CHECK in `on`, `off`,
`mixed`; NULL on every existing row) and `write_lbp_note` (TEXT). Nothing to guard: no existing
value or CHECK changes, and no table is rebuilt. Migrations are forward-only: there is no
downgrade past 041.

## #498: a streamed restore feeds dar one stream (item 180)

dar 2.7.7 to 2.8.6 misreads some archives when their slices reach it through named pipes: where one
of its reads ends exactly on a slice's last byte, it takes the slice's one-byte trailer for data,
and the unit fails `Bad CRC`, exit 5, at the same place every time (never a silent wrong restore).
Up to 1.7.1, tapectl's streamed restore gave dar a named pipe per slice. 1.7.2 joins the slices
back into the `dar -c -` stream they were cut from and feeds it to `dar -x -` on standard input,
which dar reads with a reader that has no such fault.

- **The join is the stream, byte for byte.** The stream's own 38-byte header is taken from the
  installed dar (`dar -c -` over an empty directory) with slice 1's two labels put in, then each
  slice's payload follows with its dar header and trailer taken off, then the final `T`. Measured
  identical to the original stream at slices of 1000 bytes, 64 KiB, 1M and 10G, and dar restored
  it identically on 2.7.13 and 2.7.21, each reading the other's archives.
- **Each slice is checked as it is taken apart:** its header must be slice 1's, every slice but the
  last must be the slice size, and the trailer must be `N`, or `T` on the last. A slice that is not
  what tapectl cut stops the feed and is named.
- **Item 176 holds:** every slice is still read to its end, hashed and authenticated, and dar's
  exit status decides. Holes keep their place in the stream, so dar names the files they fall in.
- **The restore no longer needs a scratch filesystem that takes named pipes.** It runs dar once
  more per streamed restore, to make the header.
- **The test** is the crafted case: one 3,000,000-byte file at the slice size where slice 1's
  payload ends on the end of one of dar's 102,400-byte reads (1,024,194 bytes with tapectl's flags
  on dar 2.7.13). It failed `Bad CRC`, exit 5, through 1.7.1's restore; the sizes a byte either
  side restored whole. With the join, all three restore whole.

No byte on tape changes. RESTORE.sh, on every tape written so far and every tape 1.7.2 writes,
still feeds named pipes; its change is 1.8.0's (item 181), and `docs/troubleshooting.md` gives the
way round on those tapes.

## Known open items

- **The real-drive acceptance:** `scripts/lbp-acceptance.sh` on home2's HP LTO-6 with the test
  cartridge EW7VWMVKF6 (`docs/lto6-validation-checklist.md`, "LBP on the real drive"), run with
  `--r1-only` first. R1 decides item 175's switch: if the HP returns no valid CRC for blocks
  written without LBP, the build that ships must carry the fallback policy
  (`LBP_R_POLICY = OnlyConfirmOfLbpWrite`), and the run says so.
- **Item 164's heir read on an armed page is unmeasured** (its fact correction of 2026-10-26): what
  was measured on the HP was a read with the page off and st at 524,292 bytes, not RESTORE.sh's
  524,288-byte reads with the page left armed. On mhvtl that read hangs at BOT for over a minute
  (EIO past it). Step 5 of the acceptance measures it on the real drive, every heir read under a
  time limit, and a hang is a FAIL.
- **The mhvtl rehearsal's rewind before an open** (`mhvtl_rewind_first` in
  `scripts/lbp-acceptance.sh`) worked around the probe 1.7.2 now sends at BOT; it is harmless and
  can go once the rehearsal passes without it.
- **`drive status`** sees a tapectl that takes the drive during its look only through the drive
  lock of its own catalog home: one running under another `TAPECTL_HOME` (the acceptance's
  scratch home) in that window is not seen.
- **ADR-0012 item 176:** 1.7.2 is built on 1.7.1, which is on 1.7.0 with #497's fix; that
  RESTORE.sh re-pin is 1.7.0's, and 1.7.2 moves no pin of its own.
