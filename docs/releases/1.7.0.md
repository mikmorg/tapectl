# tapectl 1.7.0: release notes

What changed between `v1.6.0` and 1.7.0, for the person who runs tapectl. The record is
`git log v1.6.0..` on the 1.7.0 tree, issues #478, #409, #488, #489, #490 and #497, and ADR-0012
items 121-146 and 176-178 (with items 82-95, the spanning design they build).

- **A unit may span tapes, if it allows it** (#478). Spanning is off by default. A unit opts in
  through the policy key `allow_spanning`, resolved like the other policy keys: the unit's dotfile
  `[policy]`, then its archive set, then `[defaults]`, and `false` when none sets it (item 82).
  - The run of one stage set's slices on one tape is a *range*. A version held as ranges is
    restored with every slice, 1 to N, in slice order, from the tapes that hold them.
  - Units that allow spanning go last on a tape (items 83 and 95). The drive's early warning ends
    the tape inside such a unit, the slice in flight finishes, and the tape seals short (1.6.0's
    short seal). The rest of the unit continues on the next cartridge (item 84).
  - The plan never splits a unit. A unit that does not allow spanning is still never split, and
    is cut and written whole elsewhere, as in 1.6.0.
  - A span is planned only on a drive that declares `post_warning_bytes`. On a drive without it,
    a unit that allows spanning and would pass the fill ceiling is refused, and the refusal names
    the key (item 123).
  - A unit that allows spanning may be larger than one tape (item 94). It starts early enough on
    its first tape to touch the fewest tapes, and is refused only when it is larger than the
    staging area (item 85). A unit that does not allow spanning is still refused above one tape.
  - **Changed from the ruled design, for the CTO's note:** a whole unit that a queued spannable
    unit pushes past the fill ceiling waits for the next tape, staged, instead of being refused.
    This is the coordinator's amendment of fork X12 (2026-10-23): a refusal would have made
    `allow_spanning` refuse writes that 1.6.0 accepted. A unit that 1.6.0's own plan could not
    hold is still refused.
- **A tape whose plan holds a slice of a spannable unit fences out older readers** (item 124).
  Its File 0 and seal state `requires = ["short-seal", "spanning"]`, so a 1.6.0 RESTORE.sh or
  tapectl refuses it by name. Every other 1.7.0 tape states `requires = ["short-seal"]`, as 1.6.0
  did, and a 1.6.0 reader still reads it. 1.7.0 reads every older tape as before.
- **RESTORE.sh restores a unit across cartridges,** by default through scratch space that holds
  only ciphertext, or with `--stream-tapes` through pipes (item 132). **tapectl's own restore**
  asks for each cartridge by label, sticker and chip serial (item 131).
- **Copies are counted slice by slice** (items 76, 127 and 138). A version is as covered as its
  least-covered slice. With whole writes only, every count is the 1.6.0 count.
- **Staging is released slice by slice** for a unit that spans (item 129).
- **`report failed-stages`** lists each stage attempt that failed and the hours it lost (#409,
  item 91).
- **A whole restore of a unit of many files is no longer called a failure** (#497, items
  176-178): RESTORE.sh and tapectl's streamed restore both read what dar leaves of the last slices,
  and dar's exit status decides. Tapes written before 1.7.0 keep the old script; the troubleshooting
  guide and the Heir Kit say what to do on them. See below.
- **One catalog migration, 039.**
- **Issues this release finishes:** #478 (its real-drive proof passed on home2 on 2026-10-27), #489,
  #490 and #497. #409 closed on 2026-10-17 as an accepted cost; its report of failed stages ships here (item
  91).

## On-tape changes

The golden pins moved under ADR-0012 item 135 (the CTO pre-authorized exactly the moves items
121-134 name):
- **RESTORE.sh** moved five times: three as spanning was built, under item 135 (`d9787a4f…` (1.6.0) →
  `16a21522…` → `7f1b7db0…` → `39d2535e…`), once for the fresh read of File 1 (`707c5c87…`), and
  once for the damage-handling fixes of item 145 (`1cd5a405…`, below). The 1.6.0 script is kept, byte for byte, as a test fixture
  (`tests/fixtures/restore_sh_1_6_0/`), and the tests prove it refuses a span tape by name. No
  `TOOLS_*` line moved.
- **A new pin** covers MANIFEST.toml's range block
  (`manifest_toml_range_block_bytes_are_pinned_except_created_at`). The pin of whole-unit blocks
  did not move.
- **A new meaning pin**, `a_span_tapes_short_seal_parses_short_and_fits_a_span_placeholder`: a
  short seal that states both features parses by S1-S6 and fits a placeholder that states both.

**File 0 and the seal** state `requires = ["short-seal", "spanning"]` on a tape whose plan holds
a slice of a spannable set (`volume-format-v2.md` §1.2). The spelling is normative: double
quotes, a comma and one space, in that order. The fence follows the plan, because the plan is
all that is known when File 0 is written. So a tape states it whether its plan holds the set
whole (the middle tape of two copies across three tapes, item 93) or a run of it, and whether or
not the tape ended before any of the set's slices. The seal states the same list as File 0,
read back from the File 0 the build froze.

**MANIFEST.toml.** A spannable set's `[[units]]` block, in every envelope that lists it, states
`may_span = true` on the line after `stage_set_id` (item 125). It lists every slice of the set,
1 to N, with its sizes and both hashes. `tape_position` is given only to the slices this tape's
plan holds, and is absent (never `0`) for the others. A block without `may_span` is a whole-unit
block, byte for byte as in 1.6.0. So any tape of a span gives every slice's ciphertext hash, and
a reader accepts another tape of it by that hash alone (item 88).

**What a tape holds of a spannable set** (`volume-format-v2.md` §4.4): its slices with a
`tape_position` at or before the seal's `ended_after`. All N: the tape holds the version whole
and is a copy (`completed`). Some: it holds a range (`range`). None: the set is cut on this
tape, as in 1.6.0 (`cut`).

**RESTORE.sh:**
- **It knows `spanning`** (`KNOWN_FEATURES="short-seal spanning"`), and its "needs" text names
  tapectl 1.7.0.
- **A slice with no `tape_position` is on another tape.** It is never read from this tape and
  never reported as damage.
- **A unit across tapes** (`--restore --unit NAME`, or the lone unit) is restored starting from a
  tape that holds its slice 1. Started on a tape whose range starts later, it refuses before
  reading a slice, and names the holders of slice 1 when an index the key opens names them. A
  tape that holds the version whole restores it alone, as any whole unit.
- **The default mode** reads each tape's slices into a scratch directory (inside `--to`, or
  `--scratch DIR`), still encrypted, each checked against that tape's front index. When the
  tape's run ends, it names the slice it needs next and the holders an index names, and waits
  for the next cartridge and ENTER. When every slice is in scratch, one dar run decrypts them in
  slice order through pipes, so only ciphertext is ever at rest. The space check counts the
  version's whole ciphertext before the first slice is read. When the room is not there, it
  refuses and names `--stream-tapes`; it never chooses the stream itself (item 88).
- **`--stream-tapes`** feeds one dar run through pipes across the cartridge changes, with no
  slice kept on disk.
- **Both modes** take a further cartridge only by hash (R8): its seal is read first, and it must
  list the next slice's `sha256_encrypted` in its front index at a position the seal covers.
  Anything else is named, and the prompt asks again. The prompt reads its answer from stdin and
  has no time limit. No tape device is held open across it.
- **Both modes need a dar that reads slices through pipes:** dar 2.7.9 or later when the
  envelope holds the unit's catalogue, otherwise 2.7.21 or later. An older dar is refused
  before a slice is read. There is no fallback that keeps decrypted slices on disk.
- **`--slices-from` and `--swap-tapes` do not combine with a restore across tapes.** It takes
  every slice by hash and asks again for one that fails.
- **`--restore --path`** of a unit across tapes reads the slices it needs from whichever tapes
  hold them, the tape in the drive first. They wait in scratch, still encrypted, until all are
  read, and are then decrypted for dar.
- **`--restore --all`** restores the whole units and names each unit it holds only a range of,
  with the `--restore --unit` command that restores it across tapes.
- **`--list`** says which slices of a spanning unit this tape holds. **`--where` and `--find`**
  print a holder's slice run when it is not the whole version, and do not count a range as
  holding the version.
- **`--fill-from`** takes files only from a tape that holds the version whole, and refuses a
  range by name (item 143).
- **`--swap-tapes` and `--fill-from` read each offered cartridge's seal first** (R5, R8), every
  cartridge, and take a slice only at a position its seal covers. A tape that holds a range, or
  the version whole, supplies any slice by its hash (item 139).
- **One `NOT ON TAPE` line** for a short tape's planned files past its end, under `--info` and
  `--verify`, on every short tape, span or not (item 140):
  ```
  NOT ON TAPE  files K+1 to M  (planned; the tape ended after file K, and its seal marker is file K+1)
  ```
  1.6.0 printed one line per position. It is still not a failure.
- `--info` and `--verify` otherwise read a range as data slices, unchanged.

**File 1**, on every tape 1.7.0 writes: its glossary entry for `requires` names both features,
and a new section, "A unit across tapes", says what a range is, that a restore needs every slice
1 to N in slice order, that it starts from the tape holding slice 1 (which `--where` on the
newest tape names), that a tape is accepted by hash, and what each RESTORE.sh mode needs. Its
query of the Heir Kit's catalogue lists `range` writes, with their slice runs, beside whole
copies (item 141). "If a slice or a file is damaged" says `--swap-tapes` reads the other
cartridge's seal first.

**RECOVERY.md**, in an envelope that lists a block stating `may_span = true`: a section "A unit
across tapes" says which slices this tape holds and how a restore takes the rest by
`sha256_encrypted`. The units table counts only this tape's slices of such a unit, and its
manual steps name each slice that is on another tape and never read one. Whole-unit rows and
steps did not change.

**`index/units.tsv`** (§1.5): a `range` write is a holder, and `first_slice`/`last_slice` state
the run each volume holds. The columns existed since 1.3.0, as `1` and `num_slices`.

**What did not move:** the short-seal pin (`4e126a22…`), File 3 (the front index has no new
entry type), the seal's grammar and parse rules S1-S6, whole-unit MANIFEST.toml blocks,
`layout_version` (2) and `magic`. Nothing new is readable without a key (item 126): the one
plaintext difference is `spanning` in `requires`, which never says which set, which slices or
whose.

### The heir-facing change

**Under `--swap-tapes`, a second cartridge with no readable seal now gives no slice.** 1.6.0 read
the seal first only on a cartridge that requires `short-seal`, and took a slice from any other
cartridge by its hash. 1.7.0 reads every offered cartridge's seal first and takes nothing from
one whose seal cannot be read, such as a tape whose 1.5.0 write aborted before its seal. A sealed
1.5.0 tape is read by its seal, as before. `--slices-from` with files read off such a tape by
`dd` still works: it reads files, not tapes, and accepts each by its hash alone.

### RESTORE.sh's damage handling, fixed (ADR-0012 item 145)

Two defects from 1.3.0 (#480), which GitHub's Ubuntu 26 runner exposed, are fixed:
- **A damaged file could go unlisted, and a fill could say FILL COMPLETE over it.** The per-file
  check parsed `sha256sum -c`'s report, and a `sha256sum` that shell-quotes a name holding a space,
  a colon or a TAB (Ubuntu 26.04's does) left that file off `.tapectl-damaged-files.txt`. Each file
  is now hashed on its own, and no name is read back from any tool's output. The cost is one hash
  process per restored file: a unit of 100,000 files takes some minutes more to check.
- **A folder whose own entry was in the lost slice** (dar restores nothing in it) no longer makes
  the fill refuse its own list. With an index, the list names what the index records under the
  folder. Without one (a tape written before 1.3.0), the fill restores what is missing in the folder
  and overwrites nothing.

A fill also reads the slices of every folder above a listed path, without which dar restored
nothing inside such a folder. tapectl's own restore was not affected by either defect.

### A unit of many files: a whole restore was called a failure (#497; ADR-0012 items 176-178)

Found by step 5 of the real-drive proof on 2026-10-26. Given a unit's isolated catalogue (`-A`,
which every tape since 1.1.0 carries), `dar --sequential-read` stops reading where the file data
ends and exits 0. It never reads the archive's own catalogue at the end of the last slice, nor the
last slices whole when that catalogue is larger than a slice. Once that unread part was larger than
a pipe holds (64 KiB, a unit of more than a few hundred files), RESTORE.sh ended
`FATAL: dar extraction failed (exit 0)` after restoring the unit whole, and tapectl's streamed
restore failed with `dar stopped reading slice <n>`. On home2 a unit of 9843 files and 135 GB
restored identical to its source, and RESTORE.sh then called it a failure. A unit of a few hundred
files or fewer was never affected, which is why every earlier test passed.

From 1.7.0 both read what dar leaves of a slice, and every slice after it, to its end: hashed,
authenticated by age, and the plaintext dropped. dar's own exit status then decides: 0 goes on to
the per-file check, anything else is a failure as before, with dar's message. Damage in the part
dar does not read still ends RESTORE.sh's restore as damage; tapectl records it as damage and
judges the restore by the files. The golden RESTORE.sh pin moved once for it (item 176,
`25505925…`). Nothing else on tape changed.

**Tapes already written are not rewritten** (item 178), keepsake's two among them. Their restores
are sound: dar's summary says 0 failed, and age authenticated every byte dar read. The script
stops there, though, and under `--all` it does not reach the units after that one. What to do is in
`docs/troubleshooting.md` ("RESTORE.sh: `dar extraction failed (exit 0)` after a whole restore")
and, once regenerated, on the Heir Kit's cover sheet. In short: restore the remaining units one
`--unit` at a time; for a checked restore use `--slices-from` with an empty directory where
`./RESTORE.sh --help` lists it (tapes from 1.3.0), otherwise tapectl, whose restore after a
`catalog rebuild` spools. keepsake's tapes carry 1.1.0's script, which has no `--slices-from`.

## tapectl changes

**The policy key.** `allow_spanning` is a bool in `[defaults]` (false when absent; `init` writes
`allow_spanning = false`), in an `[[archive_sets]]` table and on `archive-set create|edit
--allow-spanning true|false` (left out, the set defers to `[defaults]`), and in a unit's
dotfile `[policy]`, where `false` keeps a unit whole even when its archive set allows spanning.
`archive-set info` shows it. Misspellings (`allow_span`, `allowSpanning`) are refused by name at
every layer. `unit tag` and `unit rename` keep the key.

**`volume write`:**
- It plans a span. On each tape, in this order: the slices a span in progress still owes, as
  one unbroken run from the lowest owed slice to the highest (item 122); whole units; units that
  allow spanning, last. The first spannable unit to cross the plan bound is planned to its end,
  and nothing is planned after it. A volume holds at most one unbroken range of a stage set.
- Whether a stage set's write may span is decided when the write is planned, and stored on its
  row (`writes.may_span`). The build, the seal, confirm and resume read the row and never
  resolve the policy again; a rebuild reads the tape's `may_span`. A set that already has a `range` row is planned as spannable even
  after the key is turned off, so a span in progress can always finish.
- **It now resolves each staged unit's policy.** A malformed dotfile, or a misspelled key in it,
  refuses the write by name (#105's rule). **An edge case:** when a unit's source directory is
  missing at write time (unmounted, moved), its dotfile is not there to read, and the policy
  falls back silently to the archive set and `[defaults]`. A dotfile's `allow_spanning = false`
  is then not seen, and the unit may span if its archive set or `[defaults]` allows it. (A
  dotfile's `true` is likewise not seen, and the unit is written whole.)
- Before the tape moves, it names the units that may span past the fill ceiling and the whole
  units that wait for the next tape. After a sealed write it names each range with its slice run
  and, when a range completes a whole copy across tapes, the tapes to keep together:
  ```
  keep these together: "b" v1 is whole across SP-1 (slices 1-2) and SP-3 (slice 3). Together these tapes are one copy of it, and restoring it needs every one of them (ADR-0012 item 134)
  ```
  A short seal's report adds, after the cut units:
  ```
  Held here as a range, the rest of each still staged: <unit> (slices F-L). An ordinary `tapectl volume write <label>` onto another cartridge of the same generation continues it.
  ```
  A batch with no unit that may span prints what 1.6.0 printed.
- **Refusals,** each before the drive is touched:
  - no `post_warning_bytes`, and a spannable unit would pass the fill ceiling (item 123);
  - a run that does not start at slice 1 onto a cartridge of another LTO generation than the
    range it continues, naming both (item 86);
  - a slice the tape must write whose staged file was released, naming `tapectl volume
    read-slices --from <holder>` to stage it again (#402's shape).
- A tape that sealed full and holds a range (a continuation) says so. The `write_completed`
  event's details name the range units.
- `volume rewrite` never writes a range: it plans every unit whole and never past the fill
  ceiling, so a spannable unit it carries is cut if the early warning comes, as in 1.6.0 (item
  142).

**`volume plan`**, when a staged unit may span, shows the order one write of everything staged
takes (owed runs, whole units, units that may span), the slices each plans, where each sits
against the fill ceiling, and the units that would wait. Otherwise its output is 1.6.0's.
**`volume info`** shows a range on a `Ranges:` line of its own, never among the units carried
whole. **`volume list`**'s MIN COPIES counts a range write's unit.

**`stage create`** admits a unit that allows spanning whatever its size against one tape (item
94). It refuses one larger than the staging area, the staging filesystem's total size (not its
free space), by name, because a spanning unit is staged whole before its first tape is written
(item 85). A unit that does not allow spanning is still refused above one tape; the refusal now
names `allow_spanning` and `post_warning_bytes` instead of saying spanning is not built.

**Staging is released slice by slice** for a stage set that holds a range (item 129). Each slice
whose copies meet its unit's copy floor is released on its own, recorded in
`stage_slices.released_at`; the set becomes `cleaned` when its last slice is released. Slices
1..K need not wait for tape 3.
- `volume write`, `volume resume` and `collection run` release them after a write and name the
  slices released and the slices kept short of copies. `staging clean` releases the spans in
  scope the same way, and `--force` still releases a set whole. `staging status` shows a partly
  released set.
- `stage create --version` names the slices still short (`SlicesShort`), what continues the span,
  and why `--force` would orphan the sealed ranges.
- The #402 checks accept a missing slice file only when it was released; an unreleased missing
  file is still refused. A missing slice of a set that holds a range names `volume read-slices
  --from` the volumes that hold it, a range holder included.
- `volume read-slices` (and `compact-read`) that stages a released slice again clears its
  `released_at`.

**`collection plan` and `collection run`** resolve the policy of every pending unit, refusing a
unit whose dotfile `[policy]` does not resolve. A unit that allows spanning is not held to one
tape, goes last in its batch, and is refused only when it is larger than the staging area, or
over the fill ceiling on a drive with no `post_warning_bytes`. A unit above one tape that does not
allow spanning is refused naming the key. The preview names the unit that spans and the units
that may, and says the cartridge count is a minimum when a batch spans. With no unit that allows
spanning, the plan is 1.6.0's. `collection run` reports the per-slice release, and now names on
stderr every file a release could not remove (#108).

**Restore** (items 89, 101, 131 and 143):
- `restore unit` and `restore file` read a version held across cartridges. The cartridge they
  start on (`--from`, or the loaded one) must hold slice 1, or the restore is refused, naming
  slice 1's holders. They choose the fewest cartridges in slice order (in service before a
  quarantined last resort, a whole copy first), ask for each by label, sticker and chip serial,
  and stream the slices into one dar run across the swaps. `--spool` reads every cartridge into
  scratch first.
- A version with any slice on no live volume is refused before any prompt, naming the slices
  and where the catalog last saw them.
- With nobody at the terminal, a restore across cartridges is refused before a key is loaded or
  a slice read: tapectl changes no cartridge without a person, and `--yes` cannot load one.
- `restore volume` restores the whole units on one tape and names the units it holds only a
  range of, with the `restore unit` command for each. `--unit` naming such a unit is refused
  before the drive.
- A damaged slice is read from another holder of the same slice, a range included (item 101). A
  damaged file is filled only from a whole copy; the incomplete restore's account names each
  range it did not use, and why (item 143).

**`catalog rebuild --from-volume`** of one tape of a span records what that tape shows (item
130): every slice row of the set from the manifest with its hashes, positions only for this
tape's slices, and the write `completed`, `range` or `cut` by the split above, as confirm
recorded it.
- A spanning version is made `current` only once every slice of a stage set of it is on a volume
  the catalog records `sealed` (item 128).
- **Item 144:** the rebuild also promotes a snapshot it finds `staged`, upward only, by that
  rule, and logs it as confirm does. So a span rebuilt tape by tape, in any order, ends
  `current`. A rebuild still never changes a volume's status.
- The to-do list names a spanning version's slices no rebuilt tape holds, and the tapes that
  this tape's index names for them. The report names each range with its run and the versions it
  made current.
- Attestation (`--key <escrow>`) reads the lowest-numbered slice this tape holds.
- `catalog locate` lists range holders beside whole copies, with a `Holds` column (`whole`, or
  the run of slices).
- The adoption of a lost write (`volume resume`, #360) accepts a `range` row, splits it as
  confirm does, and promotes by item 128.

**Rewrite, compaction and verify:**
- `volume rewrite`, `volume compact-read`, `volume compact-finish` and `volume compact` refuse a
  volume that holds a range, by name (unit, version and slice run), before the drive is opened
  or anything is staged (item 133). `report compaction-candidates` and `audit`'s
  `compaction_candidate` leave such a volume out.
- A full `volume verify` marks a `range` write read back in full, as it marks a completed one
  (item 127); a quick verify marks nothing. A verify's figures count range writes.

**`audit`:**
- **`span_in_progress`** (warning, item 128) names a spanning version that is not yet current,
  the slices of it on no sealed volume, and the sealed volumes that hold the rest with their
  runs.
- **`short_seal`** gains four invariants of a `range` row: `range_without_may_span`,
  `range_written_past_ending`, `range_not_one_run` and `range_without_written_slice`. Each is a
  warning, named per volume. A catalog confirm, a rebuild or an adoption wrote never trips one.
- **`verify_age`** is per slice for a set that holds a range: each slice is dated by the newest
  full readback among its holders, and the set by its oldest slice. A set with no range is
  judged as in 1.6.0.
- `encryption`, `escrow_identity_mismatch`, `escrow_kit_stale` and `volume_verify_age` count a
  range write as a finished write. Escrow coverage and tenancy read a range as written.

**Reports:**
- **`report failed-stages [--json]`** (new; #409, item 91): every `stage create` that ended
  without staging its unit, with its unit, version, start, the last moment the catalog recorded
  of it, the hours between, and the total. It is derived from facts the catalog already keeps.
- `report summary`'s `Writes:` line counts completed writes and ranges apart when there is a
  range: `Writes:     1 completed (each a version whole), 2 range(s) (part of a version across
  tapes)`.
- `report copies` lists a current version's range holders and names each under the unit, on a
  `ranges:` line with its slice run.

**The retire family and deletion:**
- The retire floor protects a span in progress (item 128): a version with a range on an eligible
  volume is at stake when that volume alone holds any of its slices. The refusal names it as a
  span in progress, and its remedy is to finish the span with the next `volume write`.
- `snapshot delete` refuses a version with a `range` write, as it refuses one with a completed
  write.

**Copy distinctness** (items 127 and 134): when the stage set being written has a range, the
shared-place warning names only a holder of the slices the write takes next (the set's
least-covered slices). A range that holds none of them is part of the same copy and draws no
warning. A range holder is named with its slice run.

**Also in 1.7.0:**
- **#490:** `volume info` names a short ending and the cut units (`Ended short: after tape file
  K, at the drive's early warning`, then `Cut (not on this tape): …`). `restore raw-volume` on a
  tape that requires `short-seal` and has no seal it accepts ends the dump at END OF DATA when the
  drive proves it (§4.2 R2), where it used to fail at the first position past it.
- **#488, the drive phase's hooks** (every build): each `wrote file` line of a write gains
  `gap N ms` (the time from the previous file to this file's first block) and, for a slice,
  `position row N ms`. A traced write (`TAPECTL_PIPELINE_TRACE=1`) names each staged file in
  its trace. `TAPECTL_EXP_CROSSFILE=1` carries the write queue across files in a `research`
  build only.

## Costs

- **RESTORE.sh's default mode for a unit across tapes** needs scratch space for the version's
  whole ciphertext, as well as room for its files under `--to`. `--stream-tapes` needs none, and
  needs the cartridges at hand.
- **`--swap-tapes` and `--fill-from`** wind each offered cartridge to its seal before its first
  slice: one more wind per cartridge on a tape that does not require `short-seal`.
- **`volume write` with a unit that may span** builds the Layout, envelopes included, a second
  time when the plan defers or reorders a unit: the first build is a probe for the volume's own
  files.
- **`audit`**: one more statement for the whole catalog (`span_in_progress`). A set that holds a
  range pays per-slice subqueries in the copy counts; that cost is not measured yet.
- A batch with no unit that may span takes 1.6.0's path and costs what it did.

## Upgrading

home2 goes from 1.6.0 to 1.7.0 in place by `docs/handoff.md` (h). In short:

- install;
- migration 039 applies at the first open;

  sets it) before any unit allows spanning;

  span tapes, and its cover sheet now says what `dar extraction failed (exit 0)` means on the
  tapes already written (#497, item 178).

Nothing in config.toml needs editing: a `[defaults]` without `allow_spanning` reads false, and
spanning stays off until a dotfile, archive set or `[defaults]` sets it. The real-drive
proof (item 137) passed on 2026-10-27, so a unit on home2 may allow spanning once 1.7.0 is
installed. There is no downgrade past migration 039.

- **#498, dar misreads some archives through named pipes** (found while fixing #497; dar's own
  defect, in every dar from 2.7.7 to 2.8.6). Where one of dar's reads ends exactly on a slice's last
  byte, dar takes the slice's one-byte trailer for data. It happens at a fixed place in a given
  archive, only when the slices come through pipes (every streamed restore since 1.1.0, RESTORE.sh's
  and tapectl's), and dar always reports it (exit 5, "Bad CRC"); it never restores wrongly in
  silence. home2's dar has no ext2/3/4 FSA support, so its archives carry no FSA records, and the
  measured chance that a unit has such a place is about 0.1-2% (more for many small files read by
  dar 2.7.13). 1.7.0 does not fix it. `docs/troubleshooting.md` and the Heir Kit's cover sheet say
  what to do: the tape is sound, and a read from slices on disk restores the unit (RESTORE.sh's
  `--fill-from` with the same tape, `--slices-from`, or tapectl's `--spool`). The fix's shape is the
  CTO's.
