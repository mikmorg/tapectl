# tapectl 1.9.2: release notes

What changed between `v1.9.1` and 1.9.2, for the person who runs tapectl. The record is
`git log v1.9.1..` on the 1.9.2 tree and #514. No byte that tapectl writes to tape changed,
there is no catalog migration, and no command or flag changed, so by the version rule (ADR-0012
item 201) this is a patch. Its one change is the SQLite built into the binary.

## The SQLite inside tapectl

- **SQLite 3.54.1 replaces SQLite 3.51.3** (#514). tapectl builds SQLite into itself through
  `rusqlite`'s `bundled` feature, and the earlier SQLite has RUSTSEC-2026-0459
  (CVE-2026-119375). A process that opens a database together with a crafted `-wal` file whose page size
  differs from the database's can read stale bytes of its own memory. tapectl's exposure was
  small: it opens its own catalog, and the on-tape `catalog.db` it reads comes without a `-wal`.
  `rusqlite` moves from 0.39 to 0.41 (`libsqlite3-sys` 0.37 to 0.39.1).
- **`rusqlite_migration` is vendored** (`vendor/rusqlite_migration`). No release of it accepts
  rusqlite 0.41 yet, so its 2.5.0 source, the version tapectl already used, is built from the
  tree with only its rusqlite requirement raised (`vendor/rusqlite_migration/VENDORED.md`). The
  migration runner's code is unchanged.

Only test code had to change for rusqlite 0.41's API (hooks and tracing now take the connection
mutably). `cargo audit` reports no vulnerability.

## On-tape changes

None. Every golden pin holds.

## Catalog migrations

None. The catalog file format is SQLite's own and does not change between these versions; 1.9.1
and 1.9.2 open each other's catalogs.

## Upgrading from 1.9.1, 1.9.0 or 1.8.1

Nothing besides `scripts/first-run.sh --upgrade` from a checkout of `v1.9.2`. From 1.8.1, read
[1.9.0's notes](1.9.0.md) and [1.9.1's](1.9.1.md) first. The rollback is the binary alone.
