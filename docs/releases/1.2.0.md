# tapectl 1.2.0: release notes

What changed between `v1.1.2` and 1.2.0, for the person who runs tapectl. The record is
`git log v1.1.2..` on the 1.2.0 tree, issues #448, #449, #453 and #455, and ADR-0012's
amendment "2026-10-16" (items 71–75).

- **The re-pin release.** Generated on-tape text changed: RESTORE.sh, File 1 and
  RECOVERY.md. Under the version rule of 2026-09-30 the minor moves when generated on-tape
  bytes change. The CTO approved the re-pin and its exact contents on 2026-10-16 (items
  71–74). Nothing else on a tape moved: File 0, the front index, the seal marker, the
  envelopes, MANIFEST.toml, the on-tape `catalog.db` and the slices are written as 1.1.2
  writes them.
- **Two earlier rulings ride along** (item 75): the 365-day full-readback clock becomes the
  code default (#453), and `collection run` gains a snapshot hook for a living source
  (#455). Neither touches the tape.
- **No catalog migration.** The catalog stays at schema 036, as at `v1.1.2`: this release
  adds no file under `src/db/migrations/`. A 1.1.2 catalog opens as it is, and a 1.1.2
  binary still opens a catalog 1.2.0 has used.
- **`stage create` and `snapshot create` on their own are unchanged.** Only `collection
  run` has the hook.
- **Issues this release finishes:** #448 (File 1's half; the cover sheet's half was 1.1.2),
  #449, #453 (the code default) and #455 (the hook).

## On-tape text changes

The normative text is `docs/design/volume-format-v2.md` §6, "Since 1.2.0". `layout_version`
stays 2, the magic stays `tapectl-volume-v2`, and the tape's bytes are read exactly as
before. Items 1 to 5 are RESTORE.sh and are pinned by `tests/on_tape_golden.rs`. Items 6 and
7 are generated text that the golden test does not pin.

| # | Change | What an heir sees |
|---|---|---|
| 1 | **A lone-unit restore says what else the key opened.** With no `--unit` and no `--all`, and one unit in the first envelope that opens, RESTORE.sh restores it as before. | Before it reads any slice, it reads the remaining envelopes forward only. Just before `RESTORE COMPLETE` it says how many other envelopes the key opened and how many other units they list, and names `--list` and `--all` into a new directory. It says nothing when they add no units. It skips the look, with a line saying so, when the work directory could not hold the largest remaining envelope |
| 2 | **Each mode checks the tools it runs.** One table in the generator (`RESTORE_TOOLS`) draws the script's five sets and File 1's list | `mt` (or `mt-st`) for every mode that reads the tape. `--info` and `--verify` need `dd`, `sha256sum` and `head`. `--find-envelope` adds `age`, `truncate` and `tar`. `--list` adds `dar`. `--restore --path` adds `tee`. A whole-unit `--restore` needs all of them, with `mkfifo`. A bare invocation, `--help` and an unknown mode check nothing. Before, every mode checked every tool. A test holds the Heir Kit's cover sheet to the same table |

The drive connects by SAS (some models Fibre Channel) through a host adapter; there is no USB or SATA tape drive. **Two fixed points** (item 73). RESTORE.sh's "this tape needs tapectl >= …" text stays
"tapectl 1.1.0", and `requires` stays empty (`KNOWN_FEATURES=""`). So a 1.1.x RESTORE.sh
reads a 1.2.0 tape, and a 1.2.0 RESTORE.sh reads a 1.1.x tape. Both are asserted by tests
(`format_v2.rs` over a real `build()`, and `on_tape_golden.rs`).

**The golden pin moved.** `restore_sh_bytes_are_pinned` went from
`2a09fe98d3b3a10b7a0a9113d23806070f605d8d8c23366d04edc5ffa900e36e` to
`6c7bb948869ea17a9872f5477adff6d9060e16fe8f72667d90941418bc511cec`, in its own commit
("tests: re-pin RESTORE.sh for tapectl 1.2.0"). MANIFEST.toml's pin did not move. Item 72
bounds this authorization: it ends when v1.2.0 is installed. From then on a failing golden
test is a CTO decision again, as it was after v1.1.0.

**Older tapes.** A tape written before the upgrade keeps the text it was written with. It
is not rewritten, and it stays readable by 1.2.0 and by its own RESTORE.sh. Every tape
carries the script that reads it.

## The 365-day default (#453, item 75)

`[defaults] verify_interval_days` is 365 when the key is absent. It was unset in 1.1.2,
which left `audit` silent about verification age for a unit with no archive-set interval.

- **The rules:** an archive set's own value still wins, and so does an explicit `[defaults]`
  value. A value below 1 is refused by name, as in 1.1.2. There is no off switch: a very
  large number (36500, say) is the nearest thing.
- **`init` writes** `verify_interval_days = 365` into config.toml.
- **`config check` prints the value in force** as its last human line, `defaults:
  verify_interval_days = N (…)`. In `--json`, `defaults.verify_interval_days` is always a
  number. `config show` still prints the raw file, so an absent key does not appear in it.
- **`audit`'s `verify_age` and `volume_verify_age` now apply to every unit.** The age limit
  on continuing an interrupted full readback follows the same interval, so a readback whose
  oldest read is older than 365 days (when nothing says otherwise) is read again, where
  before it was continued whatever its age.
- **What you will see after a quick-confirmed write.** A write's confirm reads back only the
  front index and the seal marker. So `audit` now warns twice: `no_full_verify` for the
  volume (as before) and `verify_age` for each unit on it, as `not verified within 365 days
  (last: never)`. The audit exits 1, a warning, which the weekly timer counts as success.
  Both clear when a full `volume verify` passes, or when the write used `--full-confirm`.
  This is expected.
- **Cost.** `verify_age` runs for every unit now. That is two more catalog statements per
  unit that has no archive-set interval, which is every unit on a host like home2.
  `tests/catalog_budget.rs` moved its `Audit` pin from 14 + 6 statements per unit to 14 + 8,
  on purpose. The set of tables `audit` reads in full is unchanged.

## The snapshot hook (#455, item 75)

A unit can be half a cartridge, so one stage can take many hours, and one file touched in
those hours refuses the whole stage (`dar --retry-on-change 0`). Staging from a read-only
snapshot of the source avoids that. `collection run` can now take the snapshot itself.

- **Two optional `[[collections]]` keys,** `snapshot_command` and `release_command`. Unknown
  keys are still refused. An empty command, or a `release_command` without a
  `snapshot_command`, is refused by name at load, in `config check` and in `config set`.
  `config check` runs neither.
- **`snapshot_command`** runs once per `collection run`, before any unit is snapshotted or
  staged. It runs under `sh -c` as the user tapectl runs as, with its standard input closed,
  and with `TAPECTL_COLLECTION` and `TAPECTL_COLLECTION_ROOT` (the canonical root) in its
  environment. It must print exactly one non-empty line on stdout: the absolute path of a
  read-only snapshot that mirrors the root's layout and is not inside the root. Its stderr
  is shown when it succeeds.
- **Refusals** come before any unit is read, naming the collection, the command and its
  stderr, and exit 2 with the tape untouched: a command that cannot start or exits non-zero,
  no line or several, output that is not UTF-8, a relative path, a path that cannot be read
  or is not a directory, a path inside the live root, or (once reading starts) a unit whose
  folder is not in the snapshot. The exact messages are in `docs/troubleshooting.md`,
  "`collection run`: snapshot hook refusals (1.2.0)".
- **What the run reads and what it records.** The run's snapshot and stage read each unit's
  folder inside the snapshot: the walk, the content match, the source check, the sha256 pass,
  `dar -c -R` and the check after dar. Every recorded path stays the real one:
  `units.current_path`, `snapshots.source_path`, the `files` rows, and the `-R` in
  `stage_sets.dar_command`, which MANIFEST.toml carries to tape. `dar_create_reports` keeps
  dar's command as it ran, with the snapshot's path.
- **`release_command`** (it needs `snapshot_command`) runs when the run's staging is over,
  whether it succeeded or not, and before any tape is touched. It gets the same variables and
  `TAPECTL_SNAPSHOT_PATH`. It is best effort: a failure is a warning on stderr, `warning:
  collection "…": release_command `…` failed …`, followed by `The snapshot at … may still
  exist; remove it by hand.`, and `snapshot_release_warning` in `--json`. It does not run
  when `snapshot_command` itself failed, because nothing was taken.
- **`collection run --json`** gains `snapshot_path` and `snapshot_release_warning`.
  **`--dry-run`** prints `snapshot_command (would run before any unit is read; not run now):
  …` and runs nothing. Its `--json` carries both commands. `collection plan`, `status` and
  `sync` never run either command.
- **The recipes** (btrfs, LVM, ZFS), the sudoers entry a script that mounts or snapshots
  needs, and the root-is-a-subdirectory case are in the operator guide, "A snapshot hook for
  `collection run`".
- **The threat model's program list** gains `sh -c` over the operator's own command line
  (`tests/sg_boundary.rs` pins it): tapectl does not choose what it runs.

## Catalog migrations

None. The schema stays at 036 (`cleaning_cartridges`, added in 1.1.1). A host coming from
1.1.0 gets 036 on its first open, from the 1.1.1 changes this release includes; see
`docs/releases/1.1.1.md` for it and for why there is no downgrade past it.

## Residuals

- **ZFS's `.zfs/snapshot` path is refused as inside the root.** With `pool/media` mounted at
  the collection root, its snapshot is readable under the root. Clone it or bind-mount it
  read-only elsewhere, and print that path.
- **A SIGKILL leaves the snapshot,** and so does a second signal (which stops tapectl at
  once). `release_command` never runs then, and nothing prints a warning. A first Ctrl-C,
  SIGTERM or SIGHUP stops the staging at its next safe point, and the release still runs.
- **The lone-unit survey adds envelope reads to a default restore.** A `--restore` with no
  `--unit` or `--all` now reads the other envelopes after the one it used, forward only,
  before it reads any slice, and decrypts each one its key opens, in the work directory.
  It is skipped, with a line saying so, when the work directory could not hold the largest
  remaining envelope, whatever `--no-space-check` says. That flag silences the pre-read
  WARNING only.
- **The hook needs sudoers.** The user tapectl runs as is not root. A script that runs
  `btrfs subvolume snapshot`, `lvcreate`, `mount` or `zfs` needs a sudoers entry for exactly
  those commands. tapectl does not arrange one.
- **The hook is `collection run`'s alone.** `stage create` on its own keeps the
  mount-namespace recipe in the operator guide.

## Testing

- `tests/on_tape_golden.rs` pins the new RESTORE.sh, asserts item 2's five tool sets line
  by line, and asserts the two fixed points. `tests/format_v2.rs` asserts them again over a
  real `build()` and checks that File 1 of a built LTO-6 tape names the drives that read it.
- `tests/heir_restore_sh.rs` runs the new RESTORE.sh with `mt`, `dd` and `age` faked, for
  the per-mode checks, the lone-unit note and its skip, the DAMAGED wording and the work
  directory's warning. As ever, the mhvtl gate is the heir path's only test with the real
  tools (ADR-0012 item 70).
- `tests/collection_hook.rs` drives the hook through the real binary. The staging half has
  unit tests in `collection::batch` with a fake snapshot command: a file changed after the
  snapshot does not refuse the stage, and the same change without a snapshot does; every
  recorded path stays the real one; the release runs after a failed stage and not after a
  failed snapshot.
- The 365-day default has tests at the config, policy, audit and CLI levels, with a control
  that takes the key out of the file so only the code default speaks.

## Upgrading

home2 runs 1.1.0 and upgrades in place, straight to 1.2.0 (`docs/handoff.md`, (f)). There
is no fresh start. 1.2.0 contains 1.1.1 and 1.1.2, so their changes come with it. Read
`docs/releases/1.1.1.md` and `docs/releases/1.1.2.md`; they are not restated here.

1. **Back up the catalog first, with the old binary:** `tapectl-op db backup --to <path>`
   with 1.1.0 still installed. Migration 036 (from 1.1.1) is the only one the upgrade
   applies, and there is no downgrade past it (`docs/releases/1.1.1.md`).
2. **Skip 1.1.2's "set the full-readback clock once."** The default is 365 now, so the
   `config set` is unnecessary. If config.toml already names `verify_interval_days`, that
   value is kept. The first `audit` after the upgrade may warn `verify_age` for a unit whose
   tapes have had no full readback; a full `volume verify` clears it.
3. **1.1.2's drive caveat still stands** (`docs/releases/1.1.2.md`, "Before upgrading
   home2"): a seal position that cannot be read is "unreadable", not "absent", unless the
   drive reports END OF DATA there (#460). The step-12 rehearsal proves it on the HP drive
   before the next write.
4. **Tapes written before the upgrade are not touched.** New writes carry the 1.2.0 text.
5. **ADR-0012 item 72's on-tape authorization ends when v1.2.0 is installed.** After that,
   a failing `tests/on_tape_golden.rs` is a CTO decision, never an agent's re-pin.
