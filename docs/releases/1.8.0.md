# tapectl 1.8.0: release notes

What changed between 1.7.1 and 1.8.0, for the person who runs tapectl. The record is
`git log v1.7.1..` on the 1.8.0 tree, issues #388, #496 and #498, and ADR-0012 items 161-166,
174, 175 and 180-186, ruled 2026-10-25 to 2026-10-28. **1.8.0 contains 1.7.2**, which was never
tagged on its own (item 183): Logical Block Protection (#388), #496, and tapectl's half of #498
are in `docs/releases/1.7.2.md` and are not repeated here. The minor moves because the RESTORE.sh
that tapectl writes to every tape changed (items 181 and 182).

- **Everything in 1.7.2** (`docs/releases/1.7.2.md`): Logical Block Protection for every open of
  the drive, `volume verify`'s progress total, tapectl's own streamed restore feeding dar one
  stream, and catalog migration 041.
- **RESTORE.sh feeds dar one stream** (#498, item 181). Up to 1.7.x it gave dar a named pipe per
  slice, and dar 2.7.7 to 2.8.6 can take a slice's trailer byte for data there (`Bad CRC`, exit
  5, the same way every time). From 1.8.0 it does what tapectl has done since 1.7.2: it joins
  the slices back into the stream tapectl cut them from and feeds that to `dar -x -`. No new
  tool is needed.
- **Damage dar never needed stops no restore that checks out** (item 182). When dar has ended
  well and the only damage is in bytes it never read, RESTORE.sh names the slice and the tape,
  checks every restored file, and ends RESTORE COMPLETE if they all match, telling the heir to
  replace the tape.
- **When the join cannot run on the heir's host**, a unit on one tape is restored from slices
  decrypted to disk, as for a dar too old to stream, and a unit across tapes is refused before
  any slice is read.
- **One golden pin moves:** RESTORE.sh's, in its own commit (item 181), and once more for the
  fix that lets it run under Ubuntu 26.04's coreutils (item 184). File 1's text names the one
  stream. Nothing else on tape changes, and `requires` stays as it is.
- **A block the drive refuses is retried on the HP too** (items 185 and 186). After a refusal,
  tapectl asks the drive's position with READ POSITION's short form on its sg node, because st's
  own request uses a form the HP refuses. A session that saw a refusal confirms in full before
  its tape counts.
- **No catalog migration of its own;** 1.7.2's 041 is the last.
- **Issues this release finishes:** #496, #498 and, once its real-drive acceptance passes, #388.

- **RESTORE.sh** moves, under item 181's re-pin and again under item 184's, which allows fixes
  to items 181 and 182 before the tag (`tests/on_tape_golden.rs` `RESTORE_SH_SHA256`, `7285a4ff…`

  No pin covers File 1.
- **Unchanged:** File 0, `requires` (computed as in 1.7.x), MANIFEST.toml (its golden pins hold),
  the front index, the short seal and the seal, and the envelopes. A 1.7.x tapectl reads every

  `docs/troubleshooting.md` ("dar reports `Bad CRC` while every slice's checksum matched") and
  the Heir Kit's copy of tapectl are the way round #498.

## #498: RESTORE.sh feeds dar one stream (item 181)

dar 2.7.7 to 2.8.6 misreads some archives when their slices reach it through named pipes: where one
of its reads ends exactly on a slice's last byte, it takes the slice's one-byte trailer for data,
and the unit fails `Bad CRC`, exit 5, at the same place every time (never a silent wrong restore).
1.7.2 fixed tapectl's own streamed restore. 1.8.0 fixes the script on the tape:

- **One stream, one pipe.** The script joins the unit's slices back into the `dar -c -` stream
  tapectl cut them from and writes it into one named pipe that `dar -x - --sequential-read` reads
  on its standard input. The pipe is opened once, after dar starts, and held across slices and
  across a cartridge change (`--stream-tapes`). Only each slice's feed, a child process, ever
  writes to it, so dar closing it ends a writer, never the restore.
- **The stream's header is the heir's own dar's.** `dar -N -c - -R <empty dir> -an -D -Q` runs
  once a run, before any slice is read, and the script reads its header and puts slice 1's two
  labels in (the internal name, and the data name dar checks an isolated catalogue against).
- **Each slice is cut where the manifest says it ends and checked as it is taken apart:** the
  envelope's MANIFEST.toml gives every slice's plaintext size (`size_bytes`), and the script cuts
  the slice there with `head -c`; its header must be slice 1's byte for byte, every slice but the
  last must be the slice size its header records (and the manifest must agree) and end in `N`,
  and the last must end in `T`; a slice longer or shorter than the manifest says is refused, and
  so is a unit whose manifest gives no size, before dar starts. A slice that is not what tapectl
  cut stops the restore and is named. The header is read by a new awk fragment
  (`AWK_DAR_HEADER`) that makes the same checks as tapectl's `dar::slice` parser, under awk,
  mawk and gawk.
- **Item 176 holds:** every slice is still read to its end, hashed and authenticated, and dar's
  exit status decides.
- **No new tool.** The join uses `od`, `awk`, `head`, `tail` (on a file only) and `wc`, which
  File 1 has always listed, and the pipe needs `mkfifo` as before. It needs a `head` that reads
  no further than it is asked, as GNU coreutils' and uutils' do (see the next section for a host
  whose `head` does not).
- **Ubuntu 26.04** (item 184). Its default coreutils are uutils 0.10.0, and their `tail -c 1`
  never returns on a named pipe that carries under 64 KiB. The first 1.8.0 build read the last
  slice's trailer that way, and hung there: GitHub's Ubuntu 26.04 runner found it. The script now
  finds every slice's end from the manifest, so no tool reads a named pipe to find it. uutils
  `cat` and `tee` also enlarge the pipes they write to 1 MiB where the kernel allows it (GNU's stay
  at 64 KiB), which let the join run past damage before dar had closed its stream, and the first
  rule for item 182 then stopped such a restore; item 182 is now decided by dar's exit status (the
  next section). The whole RESTORE.sh suite passes under uutils, as an ordinary user and as root,
  and under GNU coreutils.
- **The test** is the crafted case: one 3,000,000-byte file at the slice size where slice 1's
  payload ends on the end of one of dar's 102,400-byte reads, computed from a one-slice cut
  (1,024,239 bytes with tapectl's flags on this host's dar 2.7.13). Through 1.7.x's script it
  failed `Bad CRC`, exit 5, on one tape and across tapes; the sizes a byte either side restored
  whole. With 1.8.0's, all three restore whole. The gate's `heir_slice_boundary_read` runs it
  from tape with the real tools.

## Item 174 on the HP drive (items 185 and 186)

1.7.2's item 174 retries a block the drive refused with Logical Block Protection armed. It asks
the drive where it stopped, then writes on from the planned start of the file holding that
position. The first full acceptance run on home2 (2026-10-28,
`docs/runs/2026-10-28-1.8.0-lbp-acceptance.md`) showed that the question never reached the HP
in a form it answers. The drive refused the hooked block, the position read failed, and the
session was left `interrupted` (exit 4) instead of retrying.

- **Why.** st's `MTIOCPOS` sends READ POSITION's vendor-specific form (service action 01h) unless
  st's `scsi2logical` option is set, which needs root. The HP answers that form `Invalid field in
  cdb` at every position, so `mt tell` fails on it too, as READ POSITION did on 2026-10-20.
  mhvtl accepts both forms, which is why the gate passed.
- **The position** (item 185) is now READ POSITION's short form, sent with `sg_raw` on the armed
  page's own sg node:
  `sg_raw -b -r 20 -t 300 <sg> 34 00 00 00 00 00 00 00 00 00`. It is the one raw command tapectl
  sends. It moves nothing and changes nothing; `docs/design/threat-model.md` §2 lists it and
  `tests/sg_boundary.rs` pins it byte for byte. When the drive's two location fields differ,
  the smaller is taken, so a retry can only return to an earlier file. sg3-utils, already
  required, carries `sg_raw`.
- **How the HP refuses** (measured on the real drive). It reports the refusal late: it took the
  bad block and four more with GOOD and refused the next WRITE (`Hardware Error [deferred] /
  Logical block guard check failed`). On the medium, the file held every block before the bad
  one and none after it, and the drive's position was the bad block's. That is the position item
  174 returns to.
- **The full confirm after a refusal** (item 186). Because the refusal comes late, the block the
  drive did not take can be in a file before the one being written. So a session in which the
  drive refused a write with LBP armed confirms in full: every file is read back against the
  front index before the tape counts as a copy. That applies whether the retry sealed the tape
  or the session was left `interrupted`, and to every `volume resume` of it, with or without
  `--full-confirm`. The session says why when it does. Each refusal is recorded as a
  `write_lbp_refusal` event on the volume.

## When the join cannot run

The join needs two things of the heir's host, and RESTORE.sh checks both once a run, before any
slice is read (`stream_check`):
- **a `head` that reads no further than it is asked** (`printf abcdef | { head -c 2 >/dev/null;
  head -c 1; }` prints `c`; busybox's reads ahead through stdio);
- **a dar whose standard-output header the script knows**: dar can write it, and it reads as a
  single-slice archive's header (flag `T`, no slice size).

When either fails, a unit on one tape is restored from slices decrypted to disk first, as for a
dar too old to stream (`spool_unit`, with its own space check), after one note on stderr:

```text
NOTE: the slices of 'photos/2019' cannot be joined into the one stream dar reads, on this host:
      this dar's standard-output header is not one this script knows.
      (the data does not start with the magic number of dar)
      They are decrypted to disk first instead, and dar reads them from there, as for a dar
      too old to stream: that needs room for the slices as well as the files.
```

A unit held across tapes keeps only ciphertext on disk, so it is refused (exit 1) before any slice
is read, with or without `--stream-tapes`, naming the reason and File 1's manual steps. File 1 says
the check exists in "Tools Required" and "A unit across tapes".

tapectl's own streamed restore (1.7.2) refuses a dar whose header it does not know, and from 1.8.0
the refusal names the way: `restore unit --spool` (or `restore volume --spool`).

## Item 182: damage dar never needed

Given the unit's isolated catalogue, dar stops reading where the file data ends and exits 0 (#497,
1.7.0); the script still reads, hashes and authenticates what dar left. Up to 1.7.x, damage found
there ended the restore FATAL, though dar never needed those bytes. From 1.8.0:

```text
NOTE: slice 3 of 'many' (tape file 12 of HEIR01) is damaged after the point this restore needed: age cannot authenticate it there (its own words are above), so its sha256 cannot match the front index either.
      dar had already restored what it needed of the unit, and ended well. The restore goes on:
      ...
>>> RESTORE COMPLETE
...
>>> NOTE: slice 3 of 'many' (tape file 12 of HEIR01) is damaged after the point this restore needed. Replace this tape.
```

- The restore goes on: the slices after it are read and checked, and every restored file is
  checked against the sha256 the index records for it.
- **RESTORE COMPLETE, exit 0,** when every file matches, with the note repeated in the closing
  summary. **RESTORE INCOMPLETE** with the damaged-files list when a file fails, as before.
- **"After the point this restore needed"** is decided by how dar ends, never by whether it is
  running at one instant. Damage found while dar's stream is open closes the stream there, with
  no final `T`, and the script waits for dar: dar ending with status 0 needed nothing past the
  damage, so the note is said and the per-file check decides. Any other end of dar is the damage
  stopping the restore, FATAL with the texts of 1.7.x. Given the catalogue, dar stops where the
  file data ends and exits 0 on a stream cut anywhere in the trailing catalogue, and exits 5 on
  a stream cut in the data (measured with dar 2.7.13 and 2.8.3); a dar that said 0 on a short stream would still end RESTORE INCOMPLETE,
  because the per-file check names every file absent from the restore or wrong. Damage in a
  slice dar never opened (it had ended) is said the same way.
- **On a unit restored across tapes through scratch space** the note names the tape file the
  slice was read from into the scratch directory, and does not say to replace the tape: the slice
  matched its tape's front index when it was read, so the scratch copy changed, or every copy holds
  the same damage. This refines item 182's "telling the heir to replace the tape" to the one case
  where the tape is known good.

- **The real-drive acceptance:** `scripts/lbp-acceptance.sh` on home2's HP LTO-6 with the test

- **Streaming without a catalogue** (dar 2.7.21 or later, a unit whose envelope holds no isolated
  catalogue) runs through the same join, but this host's dar is 2.7.13, so it is proven only with
  a stand-in dar claiming 2.7.21. The real-drive acceptance's heir step streams with the catalogue.
- **`--stream-tapes` asks for the next cartridge while dar may still be ending.** At the end of a
  cartridge's run the script asks whether dar is still running, and that answer can change an
  instant later; no fix can make it certain, because a dar about to refuse and one waiting for the
  next cartridge look alike. Usually the worst it does is one prompt for a cartridge before dar's
  own failure is said. The one other outcome: a catalogue dar refuses (#419) only after a whole
  cartridge's run sat in the pipes gets the after-a-swap text (run again without `--stream-tapes`)
  instead of the retry without the catalogue. Present since 1.7.0; larger pipes make it likelier.
- **1.7.2's known items** that are not the acceptance: item 164's heir read on an armed page, the
  mhvtl rehearsal's rewind before an open, and `drive status` under another `TAPECTL_HOME`
  (`docs/releases/1.7.2.md`).
