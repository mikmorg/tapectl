# 2026-10-28: the 1.8.0 LBP acceptance on home2, R1 and the first full run

`scripts/lbp-acceptance.sh` on the real drive: #388's real-drive proof, on a static debug build of
the 1.8.0 candidate (ADR-0012 item 183). Two runs took place:
- `--r1-only` answered R1 YES, so item 175's switch stays at `AllReads`.
- The full run passed steps 0-2 and **failed step 3**. The drive refused the hooked block as
  designed, but tapectl could not read the drive's position, so item 174's retry never ran.

The cause was proven on the drive (below) and ruled on the same day as ADR-0012 items 185 and 186.
`v1.8.0` is not tagged; the full run goes again on a candidate that carries them. The production
home, the production binary and every production cartridge were left alone.

## Why step 3 failed: proven on the drive

After the FAIL, nothing wrote the cartridge. The kernel log was read with the operator's sudo, and
a read-only probe ran on EW7VWMVKF6 as the run left it (the operator's go-ahead). The probe was
READ POSITION in three forms through `sg_raw`, then tape file 12 read back block by block against
the staged slice (staging was kept).

- **READ POSITION through st cannot work on this drive.** st's `MTIOCPOS` sends READ POSITION
  with service action 01h, the vendor-specific short form, unless st's `scsi2logical` option is
  set (`get_location` in `drivers/scsi/st.c`), and setting it needs CAP_SYS_ADMIN. The HP answers
  that form with `Illegal Request [current] / Invalid field in cdb` (kernel log, 08:50:16 CDT, the
  same second as the refusal). The probe saw the same answer at every position, at BOT too, and
  `MTIOCPOS` returned EIO at each one.
  - This is why READ POSITION "never answered through st" on 2026-10-20
    (`docs/runs/2026-10-20-lto6-profile-and-lbp.md`).
  - mhvtl's `ssc_read_position` answers service actions 0 and 1 alike, which is why the gate's
    `rust_lbp` passed.
- **The short form (00h) and the long form (06h) answer on the sg node, at the planned
  positions.**
  - At the start of tape file 12 the short form gave 6,680: 6,668 data blocks plus 12 filemarks.
  - After file 12's filemark it gave 7,437: 756 blocks and 1 filemark more.
  - The long form gave the same logical object numbers, with logical file identifiers 12 and 13.
  - Byte 0 was `30` away from BOT (LOCU and BYCU set, BPU clear) and `b0` at BOT.
- **The refusal is reported late.** The kernel log reads `Hardware Error [deferred] / Logical
  block guard check failed`. Between the step's two drive snapshots, st's `write_byte_cnt` grew by
  exactly 7,429 × 524,292 bytes and `write_cnt` by 7,430. So the drive took the bad block and four
  more with GOOD, and refused the next WRITE.
- **The medium holds every block before the bad one and none after it.** Tape file 12 read back
  as exactly 756 blocks, each equal in order to blocks 0-755 of the staged slice
  (`558d606b3211_v1_s2.4`), then the filemark, then end of data. The hooked block is block 756 of
  file 12. The drive therefore stood at the bad block after the refusal, and the close's filemark
  landed there. That position is the one item 174 returns to.
- **`sg_raw -R` is refused** (`Operation not permitted`, measured on mhvtl), so the command needs
  the node opened read-write, as `sg_wr_mode` already does.

## The rulings it led to (ADR-0012, 2026-10-28)

- **Item 185:** item 174 reads the position with READ POSITION's short form, sent with `sg_raw` on
  the armed page's own sg node. It is the one raw CDB tapectl sends: `docs/design/threat-model.md`
  §2 lists it and `tests/sg_boundary.rs` pins its argv. When the two location fields differ, the
  smaller is taken. While the page is armed, `MTIOCPOS` is not asked.
- **Item 186:** because the refusal comes late, a file before the one being written can be
  incomplete. A session that saw an LBP refusal therefore confirms in full before its tape counts:
  in the run that saw it, and in every `volume resume` of it, whatever `--full-confirm` says.
  Each refusal is recorded as a `write_lbp_refusal` event on the volume.

Neither changes a byte on tape or moves a pin.

## Measurements

These are debug builds, so the rates show the unoptimised CRC and crypto, not the drive.

- **Step 2's write with LBP on every block:** 7.3 GiB in 2 m 16 s, 54.4 MiB/s.
- **Its full confirm with LBP_R:** 3 m 05 s, 40.1 MiB/s.
- **R1's verify of the 1.5 GiB LBA-0001 with LBP_R:** 57.9 s, 26.6 MiB/s, in the full run (1 m
  03 s, 24.2 MiB/s in the R1 run). About half of that is positioning; streaming ran near 50 MiB/s.
- **Staging (`stage create`) in the debug build:** about 3.9 MiB/s. Most of the run's 55 minutes
  were staging.
- **The refused block cost little:** file 12 stopped 8.6 s after it began, against 18-19 s for
  each whole 1 GiB slice before it.
