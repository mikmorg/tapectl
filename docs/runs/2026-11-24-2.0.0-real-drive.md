production host's real drive before the tag. That work was four runs, all of which passed. The
CTO and the operator prepared the host, and the runs were driven from vm-desk1 over ssh, in a
tmux session on home2.

## Run 1: the round trip

The first-year scenario wrote a multi-tenant volume, verified it and restored each of its three
units ten ways, then ran `audit` and `fsck`.

The restores included RESTORE.sh off the tape three ways:
- with `dd`;
- with the primary key;
- with the backup key.

They also included the operator envelope, escrow, the raw volume and tenant isolation. Each
check passed by name.

## Run 2: `volume init` and `volume identify`

The runbook's `volume init --force` was not needed: the run erased the cartridge from its own
home first, so the catalog proved it blank (#444's verified-erase path, on this drive).

1. The cartridge held Run 1's sealed volume. `volume identify` named it from File 0 and said the
   catalog knew neither the volume nor the cartridge.
2. `cartridge erase` (short) read File 0 back as empty, with the chip serial unchanged.
3. `volume init T66-0001` then needed no `--force`. It found the blank proven by this catalog's
   verified erase.
4. It took the medium from the chip: LTO-6, density code 0x5a, 2.50 TB nominal.
5. `volume identify` read File 0 back and named T66-0001, layout 3, written by tapectl 2.0.0.
   It also matched the cartridge's FUJIFILM chip serial through the MAM.
6. After the close, the Control Data Protection page read `4a f0 00 04 00 00 00 00`: method 0,
   so the page was cleared.

## Run 3: the short seal with Logical Block Protection armed

Every 2.0.0 write arms Logical Block Protection where the drive supports it. It was armed here,
not fallen back: `tapectl --json volume info` reads `"write_lbp": "on"` for SSA-0001 and
SSA-0002 from the run's catalog.

After the run, the Control Data Protection page read method 0 again (`4a f0 00 04 00 00 00 00`).

**A harness fault in step 5.** The harness's `heir()` passes its own standard input to
RESTORE.sh. Under tmux, that is the terminal. So the RESTORE.sh restore of `ssa-z-tail`, a unit
whose only slice lies past the end of the tape, waited at its cartridge prompt from 17:03 to
19:55. The coordinator typed `done` at that prompt, which is the same path the chain run takes
through end of input. RESTORE.sh then went on as designed: it left the slice out and listed its
files with the tape that holds them. Nothing else in the step depended on the wait.

The fix is in `scripts/short-seal-acceptance.sh`: `heir()` reads `/dev/null`. `span-acceptance.sh`
holds its prompt open on purpose, through a FIFO, and is not affected.

For that unit, RESTORE.sh also printed tar's own "This does not look like a tar archive" with
status 2. Nothing had been fed to tar, and the per-file check decided the outcome, as the note
says.

## What the series measured

- **Staging** ran at 55.4 MiB/s on about 1.75 cores, while the drive writes at about 150 MiB/s.
  Issue #601 asks for parallel staging.
- **RESTORE.sh** restored at about 24 MB/s:
  - The time went to five passes per slice, one after the other: the tape read, `sha256sum` of
    the copy, `age -d`, `sha256sum` of the plain cut, and tar. Per 1 GiB on this host: ~7 s,
    ~8 s, ~10 s, ~9 s and ~2 s.
  - The CTO ordered the fix into 2.0.0: ADR-0012 items 308 and 309, on PR #602.
  - Its timing on this drive will have its own record.
- **The tape write** ran at 146 to 153 MiB/s with Logical Block Protection armed.

The write path's checks (#531's armed short seal, #532) used no RESTORE.sh. The other way
round: Run 3 steps 4 and 5, and Run 4 steps 2 and 5, are the heir's proof for the RESTORE.sh
above, not for the script items 308 and 309 make.
