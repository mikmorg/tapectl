## Found and fixed

- **Step 12 hung on `sudo sg_read_attr`.** home2's sudo asks for a password, and the first
  attempt waited on it unattended before anything was written. Step 12 now reads the chip
  directly when the login can open the SG node (the `tape` group can) and uses sudo only when
  it cannot (`f7ee007`). The proof ran with that change applied to the copied tree.

## Measurements (2026-10-13, release musl build of `d91260c`, CTO-approved for measuring only)

Scratch homes; staging on md3 (`/srv/google_copy`, not production's md1); page cache evicted
with `posix_fadvise` (no root). The host was not perfectly quiet (a java service up to ~6
cores, vm-desk1 ~2 cores, on 24 cores). Full figures are on the issues.
- **#366 hash threads 1/2/4/8:** archive 39–41 MiB/s at every N; hashes identical. No gain:
  the source is read ~1.7 times per stage (27.5 GiB for a 16.2 GiB unit). Keep 1; the lever
  is #364's single pass.
- **#368 jobs 1/2/4** (7 units, ~35 GiB): 13 m 08 s, 8 m 02 s, 7 m 29 s; hashes identical.
- **#326 tape:** write 100.6 MiB/s; quick confirm 214.6 s; full verify 52.5 MiB/s.
- **#426 (new, then closed):** the write used 1.505 bytes of native tape per data byte. Rerun
  with the host quiet (homorg paused, no java service), same unit and cartridge: 1.1.0 from
  tmpfs **1.0000** (write 119 s, ~140 MiB/s), v1.0.5 from tmpfs **1.0002** (232 s, ~72 MiB/s),
  1.1.0 from md3 **1.0000** (119 s). The cause was host contention, not the pipeline; the
  feed-ratio warning caught it.
